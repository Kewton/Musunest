## 0. 一言でいうと

**宣言の文法を「読める正本」として書き、そのとおりに書けるかを AI で測る。**

工場（CommandAgent）は `computed`・`validations`・`when`・`highlight` の式を書く。文法を渡せなければ M1b は成立しない。
**渡す前に、その文法で本当に書けるのかを確かめる。**

**ただし測れるのは「起きた割合」までである。原因は、この測り方では決まらない**（§4.1）。

## 1. なぜ今やるか

### 1.1 文法の正本が無い

2026-09-19 に窓口が棚卸しした結果である。

| | 状態 |
|---|---|
| 語彙ごとの意味と書き方 | **ある。** 意味の文書に 1 語 1 節。台帳（32 語・9 欄）と単体テストで、意味の節・負例・誤りコード・実装が機械的に繋がっている |
| 式に書けるものの一覧 | **ある。** 意味の文書の「computed」の節。`and`・`or`・`not`・`null` が書けないことまで明記されている |
| **演算子の優先順位と結合** | **無い。** 実装のコメントだけ |
| **式の上限** | **無い。** 実装に `maxLength: 200`・`maxDepth: 8`・`maxNodes: 64` があるのに、書き手が知る手段が無い。**数え方（長さは UTF-16 単位、深さは AST の深さ）も書かれていない** |
| **YAML の読み取り規則** | **無い。** 引用のしかた、型の読み替え、重複キー、使ってよい YAML の機能、順序を保つかどうか。**ここが曖昧だと、構造の検査に届く前に解釈が分かれる** |
| **機械可読なスキーマ** | **無い。** ピンは「AppSpec スキーマは MUSUNEST が正本」と宣言しているが、実ファイルがこのリポジトリに無い。版も v0.1 と v0.2-draft でずれている |
| **1 枚で読める文法** | **無い。** 式を書くには「computed」「string」「date」「enum」の 4 節以上を突き合わせる |

**「語彙ごとの辞書」としては体系的で、機械に守られている。「言語の仕様書」としては未完成**である。

### 1.2 人が書いた叩き台が、いまの語彙で書けなかった

[`02-l2-spec-examples.md`](./02-l2-spec-examples.md) §3.2（タスク管理）は 2026-09-15 の叩き台で、語彙が存在する前に書かれた。
2026-09-19 に見本を起こそうとしたところ、**7 つの要素が実装に無かった**（`app`・`label`・`required`・`and`・`not`・`card`・`sort`）。

叩き台は語彙に縛られていなかったので、**これは「人でも書けない」の証拠ではない**。
証拠になるのは次の 1 点だけである。

> **タスク管理を自然に表現しようとすると、人は今の語彙に無いものへ手を伸ばす。**

M2.2 で利用者の言葉を宣言に翻訳するのは工場（LLM）である。**同じところへ手を伸ばす見込みがある。**

### 1.3 検査されていない継ぎ目

|---|---|---|

## 2. やること

### 2.1 ① 文法の正本を書く

**「正本が一つであること」と「ファイルが一つであること」は別である。**
構造・式・規則は性質が違うので、**別の形式で書き、一つの版付き契約として束ねる**。

| 部分 | 形式 |
|---|---|
| 宣言の構造（7 欄と、欄ごとの形） | JSON Schema |
| **式** | EBNF（字句・構文・**優先順位と結合**） |
| 型の組み合わせ・名前解決・**上限（数え方を含む）**・予約語・語彙が閉じていること | 規則の表 |
| **YAML の読み取り規則** | 規則の表 |

- **同じ規則を 2 か所に書かない。**
- **契約全体をハッシュの対象にする**（M1a の判定 6 が要求する `pins/` の SHA-256）。
- **「機械可読」と「汎用のバリデータだけで全部の意味を検証できる」は別である。** JSON Schema の独自キーワードに押し込んでも、それを解釈する実装が別に要る。
- 言語は英語でよい（工場へ渡す契約であるため）。

### 2.2 ② ①どおりであることを照合する

**本番の判定器を増やさない。** いまの判定器は `packages/spec-engine`（誤りコード 59・負例 46・CI と publish が同じ判定を使う）である。
本番経路に第二の判定器を置くと、食い違ったときに決着が付かない。

**ただし「②が期待判定を持たない」は成立しない。**
**実装から期待値を作って同じ実装にかけると、実装の誤りを追認するだけ**である。

| | |
|---|---|
| 期待値の出どころ | **①の規則を読んで人がレビューした結果**。実装から生成しない |
| 照合の粒度 | **誤りコード単位ではなく、規則単位。** 各規則に「正例」「その規則だけを破る負例」「境界」を対応付ける |
| 優先順位と結合の確かめ方 | **AST か評価値で確かめる**（例：`2 + 3 * 4` が 14、`8 - 3 - 2` が 3） |
| 上限の確かめ方 | **直前・ちょうど・超過**の 3 点。**数え方も規則として書く** |
| **不一致が出たとき** | **契約の確定を止める。** 窓口が「仕様を直すか、実装を直すか」を決める。**自動で寄せない** |

> **注意：解析器が読める構文と、許してよい文法は同じではない。**
> 実装には「解析はできるが拒否する」構文がある。**解析器の構文一覧をそのまま①にしない。**

`verify-parity`（`.commandmate/verify.yaml` と `.github/workflows/ci.yml` の照合）は先例だが、
**あれが保証するのはゲートの名前と順序までで、中身は共通のスクリプトに集約している。**
**言語の意味の一致まで保証する先例ではない**ので、そこまで類推を伸ばさない。

### 2.3 ③ AI に宣言を書かせる

**何を測っているかを確定させるため、条件を先に凍結する。** 凍結しないと、結果が何の能力の数字か決まらない。

| 固定するもの | |
|---|---|
| 入力資料 | ①②と要件。**実装のコード（`packages/appspec-schema/src/`・`packages/spec-engine/`）と負例は渡さない** |
| **使ってよい道具** | **静的チェックを使わせるか。使わせるなら診断を返すか。** 一発生成と、診断を見て直す試験は**別の試験**である |
| **直しの回数** | 0 回（一発）か、n 回か |
| 出力の取り出し方 | 返信の中だけ。**ファイルを作らせない** |
| 時間の上限 | |
| 記録する版 | モデル・エージェント・契約・ビルド |

- **記憶を残さないため、毎回新しいセッションで実行する。** ただし**新しいセッションだけでは、読めるファイルや永続メモリまでは制限できない**（手段と限界は §5）
- **結論は「この条件のこのモデル」に限定する。** 工場（CommandAgent）へ当てはまるかは別に確かめる

### 2.4 ④ 画面まで出して評価する

**「画面が出た」「シナリオが合格した」だけでは、2026-09-19 の発端（配信側・画面側の欠落）をまた見逃す。**

**要件ごとに、どこを採点するかを先に書く。**

- 宣言の配信（`getSpec`・`getView`）
- 保存と拒否（**`when` が偽のときに断ることも確かめる**）
- 画面の操作（入力 → 保存 → 再表示）
- データと時計を固定する

**手元（dev）で描く。** staging への publish はしない——見本の SHA が変わるたびに、既存インスタンスが張り替わらない積み残しを踏む。
**スマホでの確認を抜き取りにするなら、その結果は全体の合格率に使わない。** 適用範囲を限定して書く。

## 3. 順番

**10 パターン（目的と書きっぷりを変える）× 5 回 = 50 回**（所有者の指示）。

**採点の仕組みが成立するかを、AI を呼ぶ前に確かめる。** 作ってから「自由に書かれた宣言は採点できない」と分かる順番にしない。

| 段 | 中身 | 目的 |
|---|---|---|
| **第 0 段** | **疎通確認を 1 回** | 新しいセッションの手段・出力の取り出し・記録が回るか。**成績は測らない** |
| **第 1 段** | **10 パターンの実現可能性を人が確認する** | 各要件に「人が書いた実現例」か「**現行語彙では不可能**」の判定を付ける。**付けないと、語彙不足を生成の失敗として数えてしまう** |
| **第 2 段** | **人の正誤例で採点を確かめる** | **正解例**・**静的に不正な例**・**静的には通るが要件を破る例**の 3 つを採点し、正解を通し 2 つの不正解を落とせることを確認する |
| **第 3 段** | ① を書く／② を作る（最小限から） | |
| **第 4 段** | **2 パターン × 2 回**（パイロット） | **成績の推定ではなく、受け渡し・抽出・採点・記録の故障発見** |
| **第 5 段** | **条件を凍結して 10 × 5** | 本番 |

- **言い換えの比較は、同じ要件内容で組にする。** 目的と書きっぷりを同時に変えると、どちらが効いたか分からない
- **情報が足りない曖昧な依頼は、「確認の質問を返すのが正解」とするか、別枠にする**
- **調整に使わない問題を残す。** パイロットで見つかった弱点に合わせて①を直し、同じ問題で本番をやると、既知の問題への適応を測ることになる

## 4. 採点

**先に決めておかないと、50 回まわしても集計できない。**

### 4.1 何を測るか — **因果は測らない**

**主指標：全試行を分母とした要件充足率。** 静的チェックの合格率とは**分けて**出す。

**同じところで落ちることは、文法の穴の証拠にならない。** 同じ失敗は次のどれでも起きる。

- モデルの固定的な思い込み
- **そもそも現行語彙で実現できない要件**（第 1 段で切り分ける）
- 採点側の誤り
- 文書の曖昧さ（1 か所の曖昧さが複数の失敗を生む）

**したがって、集計は「観測した失敗」にとどめ、原因は未確定として扱う。**

**文書が原因かどうかを確かめたいなら、別の実験が要る** ——
**モデル・要件・実行条件を固定し、文書だけを変えて比べる。**

### 4.2 何回まわすと何が言えるか

**同じ条件で繰り返すだけでは、原因の二分はできない。** 回数が効くのは**頻度の探索**である。

| | |
|---|---|
| 失敗率 10% の問題を、5 回で 1 回以上見つけられる確率 | **約 41%** |
| 5 回すべて成功したときの、失敗率の片側 95% 上限 | **約 45%** |
| 95% の確からしさで見つけたい場合の回数（失敗率 10%） | **29 回** |
| 同（失敗率 5%） | **59 回** |

**50 回は「探索」として維持する。因果の断定はしない。**

### 4.3 どう採点するか

**先に決める：名前と構造を指定する試験か、設計も任せる試験か。**

- **指定する試験**なら、期待値を固定して比べられる
- **設計も任せる試験**なら、**生成物と要件の対応付けが別に要る**。見本の名前や構造に依存した採点は、**正しい別解を落とす**

**どちらでも、期待値を生成結果に合わせて後から変えない。** 境界と拒否の条件も事前に固定する。

| 段 | 見るもの | 道具 |
|---|---|---|
| 1 | 静的チェックを通るか | `pnpm spec:check`（終了コードと誤りコード） |
| 2 | 配信・保存・拒否・画面まで繋がるか | §2.4 の採点対象 |
| 3 | 要件どおりの値が出るか | `scenario.json` の**仕組み** |

> **`scenario.json` は「仕組み」を流用するのであって、いまの期待値や表現力がそのまま使えるとは確認できていない。**
> 自由な命名・別のデータ構造・操作の連続・権限・時刻・画面上の挙動が表現できるかを、**第 2 段で確かめる。**

### 4.4 いちばん怖い結果

**無い語彙を発明して、それらしい YAML を書いてくること。**

静的チェックは落とすので実害は出ないが、**工場が同じことをすると、落ちる宣言を量産する**。
2026-09-19 の #159 で、ワーカーが「落とす・変える・期待値を書き換える」で通したのは、これに近い形である。
**この出方が何回あったかを数える。**

### 4.5 先に決める運用

- 合格基準
- 停止条件（どこまで悪ければ本番を打ち切るか）
- 予算（計算資源は共有である。`CLAUDE.md`「先に安い手を試す」）

## 7. 決まっていないこと（所有者の判断）

| | 選択肢 |
|---|---|
| `label` を足すか | **画面に日本語が一切出ないわけではない**——`enum` の表示名と検査の文言は日本語である。**足りないのは「項目や一覧に、識別子とは別の日本語の名前を付けること」**である（項目名は `^[A-Za-z][A-Za-z0-9]*$` に限られる）。M1.4 で足すか、後回しか |
| `and`・`not`・`sort`・`card` | 語彙を足す条件（`04` §6.1）に照らすと、いまは「見本が書けている」ので足さない側である。**③の結果が材料になる** |
| `required` | **キーが無いことと、必須入力を表せないことは別である。** 現仕様は**原則すべて必須**で、表せないのは「任意の項目」のほうである |
| ③を一発生成にするか、直し込みにするか | §2.3。**別の試験になる** |
| ④を「名前と構造を指定する試験」にするか「設計も任せる試験」にするか | §4.3 |
