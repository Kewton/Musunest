### 2.1 P3 の 2 本の中身（rubric の NG が正しいか）

- **P3-r1**：「少ない順」を書けないと正しく申告した。ただし**回数そのものも宣言から落とした**（メンバーの表は名前だけ）。要件の「回数が見られる」は書けるのに落としているので、**rubric の NG は正しい**（書けない部分だけを落とすべきだった）
- **P3-r2**：**`-dutyCount` という計算を作り、それを `ranking`（降順）の基準にして「少ない順」を実現した。** 第 1 段で人が「書けない」と判定した要件を、**いまの語彙の組み合わせで書いた**ことになる。代わりに、順位の部品は基準を `show` に含める決まりがあるので、**負の数の列が画面に出る**。rubric の「逆向き」の NG は、`ranking` を使ったら NG という作りのためで、**rubric の想定が足りなかった**。「人ごとの数」の NG は、回数が順位の部品の中にしか出ず、表と一覧を見る rubric が拾えなかったため

## 3. 見つけた故障

1. **rubric v2 が、項目の短縮形（`name: string`）を読めなかった。** 契約は短縮形を許す（`app-spec.schema.json`）が、v2 は項目を必ずオブジェクトとして読んでいた。P1-r1 の正しい宣言を「役割が見つからない」にした。v3 で短縮形を `{ type }` として読むように直した。**期待値は変えていない**（第 2 段の 13 例は v3 でも同じ判定になる）
2. 実行の手順の故障（zsh で引数が 1 つに繋がった）：試行の結果には影響していない
3. **第 1 段の「書けない」の判定が 1 つ外れた。** P3・P4 の「少ない順」は、負の数の計算と降順の `ranking` で書ける（表示に負の数が出る）。第 5 段の前に、P3・P4 の判定と rubric の扱いを決め直す
4. **rubric が「見られる」を表と一覧でしか探さない。** ダッシュボードの部品（`ranking` の `show`）に出ている値を拾えない
5. **誤った申告（P1-r2）は rubric では見えない。** 宣言は合格でも、「書けない」と言った内容が間違っていることがある。申告は宣言とは別に採点する

## 4. 次（第 5 段の前に決めること）

1. **P3・P4 の「少ない順」を、負の数の計算＋降順の `ranking` で書いたら合格とするか。** 窓口の提案：**合格**（要件の並びは満たす。負の数の列が出るのは画面の問題として別に記録し、昇順の `ranking` を語彙に足す候補にする）
2. **rubric の「見られる」に、ダッシュボードの部品の `show` も含めるか。** 窓口の提案：**含める**
3. **申告の採点**：申告が正しいか（書けない要件だけを挙げたか）を、宣言の採点とは別の欄で数える
