## 0. 一言でいうと

**LLM に書かせる量を減らし、決める量をコードへ移す。** LLM は「名前」と「選択」（選択肢はコードが閉じる）だけを出し、ID・参照・導ける欄・骨組みはコードが決め、宣言はコードが組み立てる。段どうしの契約は **評価器が確かめられる性質の台帳**（1 つの正本）から導き、直しは **一番良い版を保ち、門の失敗が厳密に減ったときだけ採る探索**にする。工場の判定に **unverified（確かめられなかった）** を足し、full／partial（満たしていない）と分ける。門（bundle-publish）・fail-closed・Plan と Build の分離・試験を宣言より先に固定する順・adapter は変えない。

## 2. 保つもの（不変条件）

- 外側は **コードが決める固定の段の列**。agent の自律判断を足さない（固定の流れが弱いモデルで有利：Agentless 2024、Anthropic の指針 2024、MAST 2025 の「設計の失敗」）。
- **試験は宣言より前に、要件と台帳から固定する。** 直す役は試験・表・要件を変えられない（独立に作った試験の検出率 25% 対 14%：Konstantinou ほか 2026）。**意味の独立の点検**（表の C3・宣言の C6）は別の会話で、期待と合否を見せない。印（Jev の J4）は助言で保証に数えない（07 §1.1・追加判断 A）。adapter は段ごとに設定できる形にしておく（D8 は保留のまま）。
- **fail-closed**：数えて推測しない。持ち越し・不一致・unverified が 1 件でもあれば full にしない。**unverified を full にしない**（#535 決定 5）。版と SHA・完全性・網羅の検査は省かない。
- **門 bundle-publish の 5 段と納品物の形（spec・manifest・要約）は変えない。** 工場どうしの近道を作らない。LLM は adapter 層（`llm.ts`・`openai.ts`）だけ。Data API を迂回しない。依存の向き `factory → spec-engine, appspec-schema`。
- **v1 の出力・要求のバイト列・終了コード・修復の道具の結果・上限の値を変えない**（契約試験。07 §3 と同じ作法）。v1.1α の既定の振る舞いも、旗が off なら変えない。
- 方法論：共通の原因と観測外の反例 → コード・契約・入力から直す（H1〜H7）→ 統合候補 1 つ → 独立レビュー → 同じ条件の前後比較と確認計測（`01` §4）→ merge。規則には理由と履歴（`why`・`since`）。

## 5. 性質の台帳の形

**1 つの性質に 1 行。** C2 の確かめ方・C2' の所属の形・C3 の受理条件・C4 の試験の型・網羅の単位・C7 の評価・外の採点との対応を、**この 1 行から導く**。台帳に無い性質は C2 の enum に出ず、C4 は骨組みを作らず、C7 は呼ばない。状態は「有効」「登録済み・未対応（→ unverified）」「削る候補」を分ける。行には規則の台帳と同じく `why`・`since`・履歴を持たせる。**正本はコード**（`packages/factory/src/v12/ledger.ts`）、人が読む写しは `methodology/ledger/properties.md`（試験が 1 要素 1 行で照らす。D2）。

| 列 | 中身 |
|---|---|
| `id`・`since`・`why` | 性質 ID・入れた wave・理由（観測した失敗の ID） |
| 要件の決まりの型 | 自然文の型の説明（例を書くときは P 番号で） |
| C2 の確かめ方 | `kind` と欄（例：`default-value` は `value`） |
| C2' の所属の形 | 必要な行の種類と数（例：enum の項目 1 行＋その entity）、分類（ruled／existence-only） |
| C3 の受理条件 | 受理する決まりの範囲・拒否の種類 |
| C4 の試験の型 | 対象の種類・operation・observes・必須の kind・**期待の型**・**データ状態ごとの値**・参照データの対象の種類・入力の形・値を LLM が埋めるか |
| 網羅の単位・C7 の評価 | 鍵（要件 × 対象 × 性質 × 検査の内容）／関数名と読む宣言の欄（コードで決定的） |

- **最初の 1 件は `default-value`（#533）。** C2 `kind: default-value`・`value`＝options のキー／所属＝enum の項目 1 行＋entity（コードが足す）・ruled／C3＝決まりが既定値 1 つだけで value が文の値と合うときだけ受理／C4＝normal・validate・observes `default-value`・期待 ok の文字列＝value・入力空・参照データ空・1 本以上・異常と境界は作らない。**値はコードだけで埋まる**（手 3。手 2 は LLM が書きコードが照らす）／網羅＝（要件・項目・normal・validate・default-value）／C7＝宣言の項目が enum で `default` が value と完全一致／外＝`enumDefault`。#533 は v1.1α の形で入れてよいが、この列を埋める形で作る。台帳への集約は手 2。
- **次に登録する候補**（§8.2 の切り分けから）：`enum-membership`（選択肢の外を拒む。C7 は項目が enum で options の集合が表と一致。入力の拒否は data-api の検査が担う。外の `labels` は表示名を見る別の観測で同値ではない。**M-03 の主因**）／`empty-aggregate`（下）／`when`（operation × action。期待は真偽。外＝`advanceAction`）／`validation-expression`（項目・entity × validate。検査は名前ではなく式が参照する項目で結ぶ。外＝`validation`）／`group-aggregate`・`scope-aggregate`・`highlight`・`view-structure`・`existence`／`state-after-set`（**登録済み・未対応 → unverified**）。

- **ID の振り方**：要件は Plan の `R-n`・`R:A:*`・`R:alt:*`（既にある）。C1 の行はコードが束ごとに振る（`E{n}`／`E{n}.F{m}`／`C{n}`／`OP{n}`／`V{n}`。種類の接頭辞＋出現順）。応答は ID を書かない。導ける欄（entity の所属・shared・網羅の単位・試験 ID・参照の整合）はすべてコード（07 D9 を継ぐ）。
- **選択肢の閉じ方**：C2 の schema は束ごとに組む——要件 ID は束の enum、性質は台帳の enum、所属は C1 の ID の enum（性質が許す種類だけ）、制約 ID は文書の enum。`value`（既定値のキー）は最初は文字列で受けコードが options の集合で照合する（fail-closed）。**写し・引用・位置の対応は要らない**（D10 を廃止。C3 の引用は拒否の根拠であって識別子ではない）。C1 を 3 束に分けるのは参照を enum で閉じるため（D3）。

- **検出の計測**（手 3 の受け入れ条件。D4）：凍結した候補の表 10 P を**原本**とし、**原本の正しさは人（所有者か実装に関与しない採点担当）が点検してから凍結**する。コードで変異（2 要件の所属の入れ替え・隣の性質への置き換え・無関係な行の追加）を入れ、**変異ごとに「誤りであり同値でない」ことも独立に点検**して凍結する（判定不能は別に数える）。C3 を原本 10 と変異体 50 に掛け、拒否率（変異体）と誤拒否率（原本）を**分母と区間つき**で出す。受入線は **変異体の拒否率 ≥ 0.8・原本の誤拒否率 ≤ 0.1（この集合に限る線。最初の計測で見直す）**。費用：最低 60 呼び出し（再試行なし）≈ 0.3 USD。

## 7. unverified の出力（#535 決定 5・D1）

| 判定 | 条件（v1.2 の制御。v1 の ⑦ は触らない。**要件・試験の全理由から集約し、強い方が勝つ**） |
|---|---|
| `full` | 検証した要件が全部通り、不一致 0・持ち越し 0・unverified 0 |
| `partial` | 不一致（評価して違った）が 1 件以上、または意味の点検の拒否が残った要件・書けないと申告した要件・`non-requirement` を受理されなかった文がある（**満たしていない、または満たしていない疑い**） |

| `none` | 静的 NG・早期停止・全件が unresolved（D15 と同じ） |

### 8.7 30 対で見分けられる差（D6）

- **独立な対の算数（参考）**：基準 0.30、両側 5%・検出力 80%、McNemar の正規近似（n = [z₀.₉₇₅√ψ + z₀.₈√(ψ − δ²)]²/δ²）で、+10 点に約 359 対・+20 点に約 96 対・+30 点に約 45 対・+35 点で約 33 対。回帰 0 でも +10 点に約 76 対・+20 点に約 37 対。段の通過率（基準 0.23）なら +40 点で約 25 対・+27 点で約 51 対。**不一致の率 ψ が増えると差の分散 ψ − δ² も増える**ので、「0.5 に近いから見やすい」とは言えない。
- **この組での判定は別**：対は独立ではない（10 P × 反復 3。P は題材 5 × 書き方 2）。**まとまりを P と定め**、P ごとの対の差の平均（10 個）と、まとまりを保った区間（P を単位にした符号の反転か bootstrap）で読む。同じ「改善 8・回帰 1」でも、改善が 3 P に集中していれば P 単位の反転の両側 p は約 0.25（独立なら 0.039）。**「不一致の対が 8 対 1 以上」は記述的な警報であって確定の信号ではない。** 非有意は「差が無い」ではなく「検出されず」。
- 主指標は変えた段の通過率の対の差と違反件数の対の差、全体の PASS の対の差は副（追加判断 B を継ぐ）。違反件数が必ず少数で済むとは言わない。劣化の疑いは `01` §4 の確認計測（同じ条件で流し直す）で確かめ、1 回の差で戻さない。指標・検定・止める条件は測る前に書く。
