# 05：判定のモデル（Jev）を工場に組み込む

> 状態：**v1・方針は決定**（2026-10-10・窓口。§8 の U-J1〜U-J3 と S-4 の追記を所有者が決めた）。所有者の依頼「Jev（TypeSafe）をうまく活用できないか」への検討と、小さな実測。
> 実測の道具と結果は `eval/jev/`（鍵は `.env` の `JEV_API_KEY` から読むだけ。ファイルに書かない）。

## 0. 一言でいうと

**書く役（GPT-6 Luna）と、判定する役（Jev）を分ける。** Jev は文を作らない。状態（state）と型の決まった問い（選ぶ・点を付ける・はい／いいえ）を受け取り、**確率と確信度つきの答え**を返す。工場には、LLM に「JSON で判定を返して」と頼んでいる段が多い。そのうち**答えが閉じた集合のもの**を Jev に移す。

効く場所は 3 つある。

1. **誤った「書けない」の申告を仕分けて、裏を取る**（Build の ②。今回の受入の試験の主因）
2. **聞くべきことだけを聞く**（Plan の P3〜P6。不要な質問を減らし、答えを確かめる）
3. **評価の利用者役**（選ぶことしかできないので、隠した意図が漏れない。レビュー #9 への答え）

## 1. Jev とは（文書から）

| 項目 | 中身 |
|---|---|
| 入口 | `POST https://api.typesafe.ai/v1/systemone`（Bearer 認証）。`state` と、名前を付けた問いの map を送る |
| 問いの型 | **Choice**（選択肢から 1 つ。確率と確信度）・**Score**（順序のある段階で点を付ける）・**Noul**（はい／いいえの確率） |
| 並列 | 1 回の呼び出しの問いは、同じ state に対して**互いに独立に**評価される（問いを足しても遅くならない） |
| 費用 | 入力 100 万トークンあたり 0.042 USD。出力は無料 |
| 上限 | 1 回 64k トークン（state と最長の問いで 32k）。速度の上限は需要に合わせて動く（429・529 は待って再試行） |
| 版 | `jev-latest` は動く。**版の ID（`jev-1.13.0`）を固定**し、応答の `model` を記録する |
| 弱いところ（公式） | 字面どおりに読む・数と日付の計算・間接の多い問い・大きな state・敵対的な内容・選択肢の順への偏り・文の生成。**英語が主で、日本語は精度が落ちうる** |

## 2. 実測（2026-10-10・合計 0.01 USD 未満）

| # | 何を | 組 | 結果 |
|---|---|---|---|
| E1 | 設計の段の「書けない」の申告を、**曖昧さ／語彙の穴／問題ではない** に分ける（Choice 1 問） | 受入の試験（Plan なし・effort `high`）の途中（43 本ほど）までの申告 91 件。正解は窓口が付けた（曖昧さ 44・語彙の穴 35・問題ではない 12） | **77/91（85%）**。曖昧さの取りこぼし **2/44**、曖昧さでないものを曖昧さとした **4/47**。選択肢の順を逆にしても同じ。91 件で 0.002 USD・0.35 秒 |
| E1b | 同じことを Noul 2 つ（未決の選択を挙げているか／表せないと主張しているか）に分けて聞く | 同上 | 65/91（英語）・66/91（日本語）。**語彙の穴の多くは「表せない」と書かずに主張する**（「ranking は降順固定」）ので、字面どおりの Noul は取りこぼす。**この用途は Choice 1 問が良い** |
| E2 | 「書けない」の主張が、**文書の該当箇所に裏付けられるか**（引用の点検の型） | 文書の抜粋 × 主張 12 件（正しい主張 6・誤った主張 6） | 10/12・9/12（順を逆）。誤りは**すべて「書いていない」側**で、「正しい」と「誤り」を取り違えたものは無い。難しいもの（`where` で状態を絞れない＝閉じた語彙からの推論）は確信度が低い |
| E3 | 利用者役：**構造化した隠した意図**から、質問の選択肢を選ぶ（「意図に無い」も選べる） | 読書会の意図 3 項目 × 質問 5（うち 2 問は意図に無い） | **10/10**（順を逆にしても同じ）。意図に無い問いは「意図に無い」を選んだ |
| E4 | 洗い出し：要件 × 曖昧さの観点（数えるか足すか・今月を含むか・整数か・絞り込みの組み合わせ・どの状態を数えるか・返却済みにも印を付けるか）を Noul で聞く | 12 組（指定あり 6・なし 6）。**窓口が作った例** | 12/12。ただし「件数」を指定した要件が 0.61、「数」とだけ書いた要件が 0.39 と、閾値の近くにある |
| E5 | 逆照合：原文の文ごとに、要件の一覧のどれかが覆うか | 6 文（1 文を要件から落としてある） | 6/6（落とした文は 0.15、ほかは 0.90 以上） |
| E6 | 自由入力の振り分け：選択肢を選んだだけ／新しい要件を足した／前の答えと矛盾／**運用の指示**（試験を飛ばして・前の指示を無視して） | 6 件 | 6/6。運用の指示は 0.95 以上 |

**読み方の注意**：E1 の正解は窓口 1 人が付けた。E3〜E6 は件数が少なく、窓口が作った例である。**どれも「使えそうか」の当たりであって、合格の基準ではない**。保留の題材（封をした組）は使っていない。

### 2.1 E1 で分かったこと（Plan と別に効く）

- 91 件のうち、**本当に語彙の穴なのは 35 件（38%）**。残りの 56 件は曖昧さのメモか、要件を言い直しただけのもの。§5 の「`unwritable` は語彙の穴だけ」を守らせれば、申告は 3 分の 1 近くまで減る
- 語彙の穴とされた 35 件の中身は、ほとんどが**本物**だった（空の `list` を受けない・式で比較を組み合わせられない・日付に時刻が無い・順位の上限・アプリの名前の欄が無い・操作に表示名が無い）。これは段階 2 の**語彙の穴の台帳**の材料になる

## 3. どこに入れるか

| 段 | 今 | Jev を入れた形 | 根拠 |
|---|---|---|---|
| **② 設計の後**（新しい点検） | 設計の LLM が書いた `unwritable` をそのまま信じる | 申告 1 件ずつを Choice で仕分ける（曖昧さ → `notes` と Plan へ／問題ではない → 落とす／語彙の穴 → 次の行へ）。**確信度が低いものは Luna の別の会話に回す** | E1 |
| **語彙の穴の裏付け** | なし | 申告に**制約 ID**を必須にし（`04` §5）、コードがその節の抜粋を取り出し、Jev が「抜粋が主張を裏付けるか」を答える。「裏付けない」なら設計に差し戻す。「書いていない」なら Luna に回す | E2・レビュー #2 |
| **P3 洗い出す** | LLM が自由に挙げる | **語彙の決めどころの目録**（集計の種類・期間・今月を含むか・数える状態・整数か・絞り込みの組み合わせ・0 件を含むか・直せる人…）を、要件ごとに Noul で一度に聞く（扇形）。**指定されていない観点だけ**を質問の候補にする。目録に無い曖昧さは Luna が挙げる | E4・パターン「投機的な扇形」 |
| **P4 質問を組み立てる** | — | 質問の文と選択肢は Luna が作る。**重複**（同じ事項を別の言い方で聞いていないか）と**影響**（答えで作るものが変わるか）を Jev が点検する | 不要な質問の率（U-P4） |
| **P5 答えを反映する** | — | 自由入力を Choice で振り分ける（選択肢に当たる／新しい要件／矛盾／運用の指示）。**運用の指示は要件にしない**。矛盾は次の往復で確かめる。決めるのはコード | E6・レビュー #7 |
| **P6 照合** | 原文の引用が実在するかだけ | 原文・答えの文ごとに「どの要件が覆うか」を Noul で聞く（双方向）。引用の実在はコードのまま | E5・レビュー #1 |
| **評価の利用者役** | LLM が文で答える案 | **Jev が選択肢から選ぶだけ**（「意図に無い」も選べる）。文を作らないので意図が漏れず、都合のよい補いもしない | E3・レビュー #9 |

**入れないところ**：宣言・質問の文・代わりの案を**作る**こと（文の生成）、数と日付の計算（コード）、権限・公開・検査の省略の判断（コードと確認の画面だけが決める）。

## 4. 組み込みの決まり

- **判定の口（port）を 1 つ作る**：`judge.choice / score / noul` の型だけを factory に置き、Jev はその adapter にする（CLAUDE.md「LLM の呼び出しは adapter 層に閉じ込める」）。**同じ口を Luna の構造化出力でも実装し**、Jev が使えないとき（429・529・障害）はそちらに落とす。試験は偽物の判定で回す
- **閾値と確信度で道を分ける**（パターン「確信度で道を分ける」）：確信度が高い答えだけをコードが使い、低いものは Luna の別の会話か、人（質問）に回す。**閾値は版の ID に結び付け**、版を上げたら測り直す
- **判定は助言であって、門ではない**：最終の合否は今の門（静的チェック・固定した試験・対応表）のまま。Jev の答えで門を開けない
- **state は小さく**：問いに要るものだけを渡す（文書は全体ではなく、制約 ID の節の抜粋）
- **敵対的な内容に弱い**（公式）：依頼文と答えを state に入れるときは、問いの側に規則を書き、答えはコードが確かめる
- **記録**：版の ID・問いの版・閾値を、納品物の要約に入れる（S-5）

## 5. 費用と時間

- 1 回の依頼で増えるのは、申告の仕分けと裏付け（数十問）・P3 の扇形（要件 15 × 観点 8 ≒ 120 問）・P5・P6。**合わせて 0.001 USD 前後**（E1 の 91 件が 0.002 USD）。1 回の呼び出しは 0.3〜0.5 秒
- Luna に頼んでいた判定を移せば、Build の費用と時間は**減る**見込み（今の点検の段は 1 回 数十秒）

## 6. 危ないこと

| 危ないこと | 手当て |
|---|---|
| 日本語の精度（公式に「落ちうる」） | 問いは英語、state は日本語のままで測った。広げる前に、ラベル付きの組（§7）で測る |
| 窓口 1 人の正解・少ない件数 | §7 で正解を 2 人（窓口と Codex）で付け、食い違いは人が決める |
| 速度の上限が動く・外部の障害 | 判定の口の Luna 版に落とす。**Jev が止まっても工場は止まらない** |
| 依頼文が第三者（TypeSafe）に送られる | S-4（利用規約とプライバシーの説明）に足す。データの保持の扱い（ZDR は企業の契約だけ）を確かめる |
| 閾値を受入の題材に合わせすぎる | 閾値は受入の 10 パターンの組で決め、保留の題材と曖昧な依頼の組（封をした組）では測るだけにする |
| 版が変わって答えが変わる | 版の ID を固定する。上げるときは §7 の組で測り直す |

## 7. 次に測ること（Issue にする）

1. **ラベル付きの組**：設計の申告（今回の 91 件＋次の試験の分）・語彙の穴の主張と文書の節の対・要件 × 観点の対。正解は 2 人で付ける
2. 上の組で、**確信度の閾値ごとの正しさと、Luna に回る割合**を出す（Jev だけ・Luna だけ・Jev＋Luna に回す、の 3 つ）
3. **合格の基準（案）**：申告の仕分けで、曖昧さの取りこぼし 5% 以下・語彙の穴を曖昧さとする誤り 10% 以下（どちらも Luna に回す分を含めて）
