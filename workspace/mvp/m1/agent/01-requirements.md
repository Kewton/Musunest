# 01：要件

> 状態：**案 v2**（2026-10-09・窓口。Codex のレビュー（[`99-review.md`](./99-review.md)）を受けて直した）。前提は [`README.md`](./README.md) §1。

## 1. 範囲

| 入れる | 入れない（今回） |
|---|---|
| 依頼文（自然文。丁寧・会話体・箇条書き）から、新しいアプリの宣言を 1 枚作る | 既存のアプリの宣言を直す（M2.4 の「追加の指示」）。**ただし入力の形は先に空けておく**（§2 の F-1） |
| 書けない要件を見分けて申告する | コードを持つアプリ（L3/L4）。宣言だけ（L2） |
| 納品物を CommandAgent と同じ形で出す | 画面の見た目の調整、画像の生成 |
| 1 回の生成の記録（段ごとの入出力・費用・時間）を残す | 利用者との対話（質問を返して答えを待つ往復）。**§2 の F-6 で扱いを決める** |

## 2. 機能の要件

| # | 要件 | 根拠 |
|---|---|---|
| **F-1** | **入力**：依頼文（文字列）と、任意で「いまの宣言」（M2.4 用。今回は常に空） | M2.4 で入力の形を変えないため |
| **F-2** | **出力**：①宣言 1 枚 ②書けなかった要件の一覧（要件の文と理由） ③**要件の対応表**（要件ごとに、宣言のどこで満たしたか） ④生成の記録 | 第 5 段：申告は宣言と別に採点した。対応表があれば人の確認が速くなる |
| **F-3** | **要件を先に箇条書きにする。** 依頼文から、1 行 1 要件の一覧（ID 付き・**原文の引用と位置付き**）を作る。**一覧で落ちた要件が無いかを、原文に戻って確かめる**（逆照合）。点検の段には原文も渡す | 第 5 段：会話体は丁寧な書きっぷりより明らかに弱かった（当番表 5/5 対 0/5） |
| **F-4** | **書けない要件は、その部分だけを落とす。** まわりの書ける要件（例：「回数を少ない順に」の「回数」）は残す | 第 5 段の本当の不合格の最大の原因（P4 の 5 本） |
| **F-5** | **無い語彙・キー・関数を作らない。** 書けないものを近い別の意味で書き換えない | `06` §4.4。第 5 段では 0 本。エージェントにしても 0 を保つ |
| **F-6** | **曖昧な依頼の扱い**：軽い曖昧さは、**どちらに決めたかを記録して書き進める**。**重大な曖昧さ**（どちらに決めるかで作るものが変わる）は決めずに「未解決」として残し、結果を部分案にする（F-11）。質問を返すかどうかは M2.2 で決める | 第 0 段の「1 冊か複数か」。対話の往復は TTSU を延ばす |
| **F-7** | **選択肢の表示名は要件の言葉のまま**使う | 第 2 段の決定 1 |
| **F-8** | **登録の操作・画面への表示を落とさない。** 「登録できる」「見られる」と書いた要件は、操作と画面の両方で満たす | 第 5 段：登録の操作が無い 3 本、計算を出さない 1 本 |
| **F-9** | **振る舞いを確かめる。** 計算・検査・操作の条件・印が、要件どおりの値を返すかを、spec-engine の評価器で試してから納品する | 第 5 段：印を付けない 3 本は、静的チェックでは見つからない |
| **F-10** | **納品物の形は CommandAgent と同じ**（bundle の manifest・headless の要約・`artifacts/app.spec.yaml`）。門（`packages/control-plane` の bundle-publish）を必ず通す | CLAUDE.md の不変条件（#273） |
| **F-11** | **結果は 3 つ**：合格（全部満たす）／部分案（書けない要件・未解決の曖昧さ・未解決の試験がある）／失敗。**部分案は、利用者が了承してから publish する**。検証の結果は、完成した宣言のバイト列に結び付ける | レビュー R-3 |

## 3. 品質の要件（**品質を優先する**）

| # | 要件 | 目標（案） |
|---|---|---|
| **Q-1** | 受入の試験（`03`）の**宣言の合格**（書ける題材） | **90% 以上**（一発生成は 77〜80%） |
| **Q-2** | 一部書けない題材の**挙げ漏れ** | **10% 以下**（一発生成は機械 25%・人 0%） |
| **Q-3** | **誤った申告**（書ける要件を書けないと言う） | **10% 以下**（一発生成は人の確認後 3/50） |
| **Q-4** | 最後の静的チェック | **100%**（通らないものは納品しない。通らなければ「作れなかった」と返す） |
| **Q-5** | 無い語彙の発明 | **0** |
| **Q-6** | **過学習していないこと**：受入の試験に使わない題材（保留の題材）でも、Q-1〜Q-3 と大きく変わらない | `03` §4 |

## 4. 時間・費用の要件（品質の次）

| # | 要件 | 線（案） | 扱い |
|---|---|---|---|
| **T-1** | 1 回の生成の時間 | **上限 5 分**（目標ではなく打ち切りの線） | M2 のゲート（TTSU ≤ 10 分）の半分を工場に割り当てる。品質を優先するので、5 分までは使ってよい。**段階 1 の評価のあいだは 10 分**（2026-10-09 所有者の決定。#296 の疎通の確認で、effort `high` の設計の段が 1 回 50 秒前後かかった）。本番の線は評価で測った数字から決め直す |
| **C-1** | 1 回の生成（ジョブ）の LLM の費用 | **上限 0.10 USD**。**呼ぶ前に最大の費用を予約し**、超える呼び出しはしない。再配送の分も同じジョブの予算に含める | 一発生成は 1 本 0.1〜0.7 セント。エージェントで 10 倍になっても収まる。**段階 1 の評価のあいだは 0.30 USD**（2026-10-09 所有者の決定。出力の上限を推論の分を見込んで上げると、呼ぶ前の予約が 0.10 USD に収まらないため。#296）。本番の線は評価で測った数字から決め直す |
| **C-2** | 1 人あたり・月あたりの上限 | **M2.2 で決める**（`roadmap.md` §5「M2.2 の前に決めること」） | 悪用で青天井にしない |
| **C-3** | Cloudflare の CPU | **LLM の応答待ちは CPU に数えない**。静的チェック・評価器・組み立ての CPU とメモリは、**段階 3 の最初に生成のジョブとして別に測る**（規模と反復を含めて。まだ実測は無い） | CLAUDE.md「計算資源は共有の予算」 |

## 5. 安全・運用の要件

| # | 要件 |
|---|---|
| **S-1** | **依頼文は命令として扱わない。** 規則とデータを分け、合否・持ち主・納品先はコードが決める。道具の引数を確かめる（`02` §2.2）。出力は語彙が閉じた宣言だけで、門を通らないものは置かない |
| **S-2** | 表示名（利用者に見える文字列）に、不適切な言葉や個人情報らしい文字列が入っていないかを確かめる（方法は `02` の未決） |
| **S-3** | **API キーは環境ごとの Secret に置く**（リポジトリ・CI・Variable に置かない）。置き場所は CLAUDE.md の表に行を足す |
| **S-4** | 依頼文が OpenAI と **TypeSafe（判定のモデル Jev。`05`）** に送られることを、利用規約とプライバシーの説明に書く（TypeSafe は 2026-10-10 所有者が決定）。それぞれの API のデータ保持の設定を確かめる |
| **S-5** | **再現できる記録**：モデル・effort・プロンプトの版・契約の版・spec-engine の版を、納品物の要約に入れる |
| **S-6** | **モデルを入れ替えられる**：LLM の呼び出しは adapter 層に閉じ込める（CLAUDE.md の不変条件） |
| **S-7** | **失敗の帰属**：「作れなかった」ときに、どの段で何が起きたかを分類して残す（M2.5 の失敗の帰属分類ログの材料） |
| **S-8** | **記録を最小にする**：既定では段ごとの要約だけを残し、依頼文と LLM の応答の全文は残さない。閲覧はジョブの持ち主の Community だけ。保持期間と削除の手順を決める。API キーは adapter だけが扱い、失効の手順を書く |
