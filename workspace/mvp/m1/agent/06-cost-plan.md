# 06：生成 1 本の費用を 0.02 USD に、さらに 0.01 USD に下げる道筋

> 状態：**案 v1**（2026-10-10・窓口）。
> 所有者の決定（2026-10-10）：**要件定義（Plan）と yaml の生成（Build）を足して、1 本あたり当面 0.02 USD・長期 0.01 USD**（LLM と Jev の合計）。**いまは品質を重視し、徐々に近づける。そのために静的解析と Jev をうまく使う。**
> 要件は `01-requirements.md` C-1a。実測の道具は `eval/cost/`。

## 0. 一言でいうと

いまの 1 本 **0.080 USD** のうち、**67% は入力**である。段ごとに同じ文書（契約・語彙の意味・台帳。約 3.6 万トークン）を毎回送り、しかも**キャッシュが一度も当たらずに、毎回 1.25 倍の書き込みの値段を払っている**。まずここを直す（品質に触らない）。次に、**判定だけの段を静的解析と Jev に移し**、LLM は「作る」ことだけに使う。

| 順 | 手 | 1 本の見込み | 品質への影響 |
|---|---|---|---|
| 0 | 今（Plan なし・effort `high`） | 0.080 | — |
| 1 | **キャッシュを効かせる**（文書の直後に明示の breakpoint・段ごとの指示を後ろへ） | 0.047 | 無し（同じ入力） |
| 2 | **文書を要る段にだけ送る**（要件にする・逆照合には語彙の文書が要らない） | 0.040 | 無し〜小（測る） |
| 3 | **判定の段を静的解析と Jev へ**（逆照合・対応表の点検・申告の仕分け） | 0.025 | 測って比べる（`05` §7） |
| 4 | **Plan を通す**（Build の「要件にする」が要らなくなる。Plan の判定は Jev） | Plan 0.006＋Build 0.017 ≒ 0.023 | 上がる見込み（`04`） |
| 5 | **試験の多くを静的解析で作る**（検査の式から境界の値を出す）・段ごとに effort を選ぶ | **≒ 0.018（当面の目標）** | 測って比べる |
| 6 | **宣言の yaml をコードが組み立てる**（LLM は構造化した設計だけを出す） | **≒ 0.010（長期の目標）** | 書き間違いが減る見込み |

1 行目と 2 行目は §1 の実測からの計算、3 行目より下は §1 をもとにした粗い見積もりである。**各段を入れるたびに受入の試験で測り直す**。品質（書ける題材の合格・誤った申告）が下がる手は入れない。

- 記録の値（0.069）は、キャッシュの**書き込み**の割増し（入力の 1.25 倍）を数えていない。割増しを入れると **0.080 USD**（予算の予約も同じだけ少なく見積もっている。§3 の Issue で直す）

### 1.2 キャッシュが当たらない理由（API で確かめた）

| 試したこと | 結果 |
|---|---|
| 今の形（段ごとに違う `instructions`・文書・データ）で、データだけを変えて 2 回 | **2 回とも 3.6 万トークンを書き込み、読み取り 0** |
| まったく同じ要求を 2 回 | 2 回目は全部が読み取り |
| **文書の直後に明示の breakpoint**（`prompt_cache_breakpoint`）を置き、段ごとの指示とデータを後ろへ。構造化出力つき | **2 段目・3 段目は 3.6 万トークンが読み取り**（書き込み 0） |

- GPT-5.6 以降の既定（implicit）は、**最後のメッセージ（データ）の終わり**に breakpoint を置く。だから、データが違えば前置きも再利用されない
- 書き込みは入力の 1.25 倍、読み取りは 0.1 倍。**今は毎回 1.25 倍を払っている**（キャッシュが無いより高い）
- 上の `instructions` には breakpoint を置けない。段ごとの指示は、文書の後ろの developer のメッセージに移す

## 2. 静的解析と Jev の使いどころ

**原則：答えが閉じているものは、まずコード（静的解析）、次に Jev、最後に LLM。** LLM は「作る」（要件の文・質問の文・設計・試験の期待）にだけ使う。

| 段 | いま | 移す先 | 根拠 |
|---|---|---|---|
| 逆照合（①'／P6） | LLM 2〜3 回（文書つき） | **コード**（引用が原文に在るか・文の範囲の覆い）＋ **Jev**（文ごとに覆う要件があるか。`05` E5） | 割合 29% |
| 対応表の点検（⑤a） | LLM が要件ごとの宣言の場所を挙げる | **コード**が宣言から候補の場所（項目・計算・画面・操作）を列挙し、到達を確かめる（今もある）。**Jev**が「この場所はこの要件を満たすか」を Noul で答える。確信度が低いものだけ LLM | 割合 22% |
| 申告の仕分けと裏付け（②の後） | なし（LLM の申告を信じる） | **Jev**（`05` E1・E2）。制約 ID の検査は**コード** | #332 |
| 要件にする（①） | LLM（文書つき） | Plan の P1（**文書を送らない**。要件は語彙を知らずに書ける） | `04` |
| 洗い出し（P3） | — | **Jev** の目録の扇形（`05` E4）＋足りない分だけ LLM | `04` |
| 試験を作る（②'） | LLM が正常・異常・境界を全部作る | **コード**が検査の式（`validation`）を spec-engine の式の解析で読み、境界の値と期待を作る（`amount >= 1` → 0・1・2）。計算の期待と、在ることだけの要件のシナリオだけ LLM | 割合 17% |
| 書く（③） | LLM が yaml の全文を書く | 当面：**文書は設計で使う語彙の節だけ**（コードが設計から選ぶ）。長期：**設計を構造化し、yaml はコードが組み立てる**（LLM は書かない） | 割合 16% |
| 静的チェック（④）・試験の実行（⑤b） | コード | そのまま | 0% |

## 3. Issue（品質に触らない順）

| 順 | 中身 | 依存 |

## 4. 危ないこと

| 危ないこと | 手当て |

| キャッシュの保持は 30 分。1 本が長いと切れる | 1 本は 10 分まで（T-1）。切れても書き込み 1 回分の割増しだけ |
