# 04：プロンプトの書き方と棚卸し

> 状態：**採用 v3**（2026-10-12・所有者が採用）。台帳の実体は [`ledger/rules.md`](./ledger/rules.md)。規則の置き場所は `packages/factory/src/stages/*.ts`・`plan/*.ts` の `*_RULES` 配列と、配列の外の定義。コードの行は main `96a691d`。

## 0. なぜ原則と理由で書くか

「X のときは Y」は、X に当たらない入力に何も言わない。理由があれば、モデルは未知の入力でも同じ方向に倒れる。条件分岐は型の欄とコードに置くほうが確実で、検査もできる。

## 1. 書き方

| 原則 | 理由 |
|---|---|
| 段の規則は「この段は何者か」「守る不変条件（理由つき）」「schema で表せない形の注意」の順に書く | 役割が先にあると、個々の文の意味が決まる |
| 条件分岐は契約（型の欄）とコードへ移す。規則には書かない | コードなら検査でき、読み落としが無い |
| 題材・値・名前・構造を名指ししない。種類の全部に掛かる文にする。見本を入れるなら違う構造の例を並べ、受入の題材の言葉を使わない | 名指しは見た題材への適応（`03` §2）。偏った例は表面の特徴に引っ張る |
| コードが決められる事実（`03` §3）を規則で指示しない。LLM が**選ぶ**ことだけを書く | 決定的なものを書かせると、取り違えが落ちになる |
| やり直しの指示（前回の問題）は規則に昇格させず、データで渡す | 規則が試行ごとに変わると、キャッシュも台帳も崩れる |
| 規則の多さや矛盾が読み落としの一因かを調べ、文を足す前に契約・コード・分割で減らせないかを見る | accept16 だけでは文数と読み落としの因果は未確定。根拠の無い数の上限は置かない |

## 2. 規則の台帳

| 決めること | 中身 |
|---|---|
| 置き場所（今） | `ledger/rules.md`。窓口が human-only で更新する。コードの PR は規則の ID と理由を持ち、窓口が台帳を対応させる |
| 置き場所（次） | コードの中。`*_RULES` を `{ id, text, why, since, modes }` の並びにし、プロンプトは `text` を結合する。単体試験で「理由と履歴がある」ことを照合する。**変更する段から始め、全規則を一度に移すことを開発再開の前提にしない**。外す口（`--drop-rules`）は CLI と評価専用に閉じ、通常の経路で不変条件を外せる口にしない |
| 数え方 | 文ではなく**定義・配列の要素**の単位。現行は配列 99 要素（`COMMON_RULES` は 5。#418 で ② が 17→22、#419 で P3 が 5→7）＋配列の外だけで使う定義 4（#418 の作り直し専用 1 を含む）＝ 103。判定の閾値は `limits.ts`・`stages/test-suite.ts`・`plan/run-plan.ts` の定義を載せる |
| 行 | ID（`R-<段>-<連番>`）・要約・種類（役割／不変条件／形／条件分岐／名指し）・なぜ入れたか（Issue・計測・レビュー。不明は「出どころ不明」）・対応するモードか契約の根拠・決定的か・削る試験の結果・状態 |
| モードが無くても残せる規則 | 役割・基本の契約・安全の不変条件（データは命令でない、無い語彙を作らない、など） |

## 3. 規則を足す条件

1. ID・理由・履歴（モードか契約の根拠）が同じ diff にある（台帳がコードに入るまでは、PR の本文に書き、窓口が台帳へ写す）
2. `03` §1 の下の段で直せない理由が Issue にある
3. 原則と理由の形で、条件分岐・名指しを含まない
4. 不要になる規則を同じ PR で消す
5. **効力の証拠**：ワーカーは、送信する文・データ・schema と台帳の整合を API 不要の試験で示す。**LLM の振る舞いへの効力は、窓口の変更前後の計測で確かめる**。偽物の LLM は固定の応答を返すので、規則の有無で応答を切り替えて「効いた」証拠にしない（合成の例の二点測定は、コード・契約・経路の修正にだけ使う）

## 4. 削る試験

| 決まり | 理由 |
|---|---|
| 同じ版・同じ条件の「規則あり」を基準にし、「規則なし」と比べて候補を絞る | 基準が無い差は読めない |
| 悪化の疑いが無いことを、合格・充足率・申告・未知の落ち・到達段を含めて見る。開発用で差が無いだけでは不要と確定せず、**回帰用でも確認してから**消す | 開発用は各パターン 2 回で、各 1 本の減少を許すと全体で大きく減りうる |
| 二分と確認の追加の本数に上限を置き、使い切った候補は残して次回へ回す | 1 束の見積もりから外れて費用が膨らむ |
| 意味の独立の点検・未知 ID や所属や版の検査・未対応を未解決にする経路は、**数だけで減らさない**。別の根拠と同等の検査ができるまで残す | 門を緩める方向になる |
| 候補の束と順は台帳に書く（本文に数を書かない） | 本文と台帳の二重管理を避ける |
| コードの検査（`check*`）・閾値・目録の観点も同じ扱いにする。台帳に出どころと守るものを載せ、基準の後に 1 束ずつ外して比べる。特定の入力にだけ効く分岐を先の候補にする | 特例は規則だけでなくコードにも入っている。門と意味の点検は上の行のとおり数だけで減らさない |

- 契機：構造の直しで事実の持ち主が決まったとき（その事実を推測していた段の規則）、受入の線を超えたあと（規則とモードの数を減らすことが目標になる）
