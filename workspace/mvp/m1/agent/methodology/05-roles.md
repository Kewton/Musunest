# 05：体制への当てはめ

> 状態：**採用 v3**（2026-10-12・所有者が採用）。体制の正本は `CLAUDE.md` と `docs/parallel-development.md`。この文書は各役割に求めることと、既存の手順への接続（差分）を決める。

## 0. 分担の理由

実装した本人が自分の直しを採点しないこと、意味の点検と門を実装の外に置くこと、人の merge が要るもの（workspace・運用文書・ゲート）とコードを分けることが、既存の手順にある。方法論はそれに乗る。

## 1. 役割ごとに求めること

| 役割 | 求めること | 禁じること |
|---|---|---|
| 窓口 | 計測を流す。台帳と評価セット・計測の道具を human-only で更新する。調査の依頼に**同じ原因の疑いがある複数の落ち**と台帳の行を付ける。単発でも契約の因果と別構造の反例を調べ、一般性を示した修正は候補にする。**各 wave の実装が揃った時点で、実装に関与しないレビュー担当へ、共通の原因の証拠と統合候補の差分を渡す。** 所有者に判断を回す | 入力に固有の規則を足す。回帰用の落ちの中身を読む。保留の組を読む |
| 調査（Claude_sub） | 複数の落ちから共通の原因（ファイル:行）と、観測の外の反例を返す。安い候補（コード・契約・入力）と採らない理由を書く。単発は「単発」と書いてよい（調べてもよい） | プロンプトの文案を最初に出す。題材の言葉を書く |
| レビュー（Codex。実装に関与しない） | 時点は 2 つ：草案・Issue 案（実装前）と、**wave の統合候補の差分（実装後）**。観点：過適合（名指し・1 本だけの根拠）／下の段で直せないか／門と意味の独立の点検を保つか／規則に理由と履歴があるか／不要になる規則が消えているか。「直さないと誤る」指摘は証跡に残す。レビュー後に候補の内容が変わったら、変更した部分の確認を取り直す | 自分が関与した実装を採点する |
| ワーカー | Issue の対象ファイルの内側でコードを直す。コード・契約・経路の修正は合成の例の二点測定で示す。規則の変更は送信する文・データ・schema と台帳の整合を API 不要の試験で示す（効力は窓口が測る） | 外部 API を呼ぶ。鍵と環境ファイルを読む。`../Musubi-workspace` を読む。題材の言葉を使う。質問の画面を出す |
| 管理 | merge の前に、証跡・CI・scope・規則 ID と理由・題材の言葉の有無に加えて、**独立レビューの証跡**を見る。直さないと誤る指摘が残る候補は merge しない。merge の時点は §3 の差分に従う。wave が終わったら窓口へ報告し、**窓口の計測の結果まで次の dispatch を止める** | 計測と独立レビューを待たずに merge する・次の wave を dispatch する |
| 所有者 | 線（受入・受け入れる基準・予算）、構造の変更、保留の組の封と使い終わり、計測の条件を決める | — |

## 2. Issue と dispatch への接続

- **コードで閉じる Issue はワーカーへ。** workspace の台帳・計測の道具・評価セット・運用文書の変更は窓口が human-only で扱い、人が読んで merge する。両方を 1 つの Issue に混ぜない（workspace を含む PR は人の merge。`CLAUDE.md`）
- Issue の追加の欄は**短い要約**にする：`## 失敗のモード`（台帳の ID と共通の原因。無い Issue は正しさの不具合・記録・契約・評価基盤に限る）、`## 直しの候補と採らない理由`、`## 効いたかの確認`（API 不要の試験の名前と、窓口が見る計測の指標）。詳細のパスは `## 参照`、変更の許可は `## 対象ファイル`、依存の番号は `## 依存` に置く（planner が読む形は変えない）
- plan の前に、実行契約の goal 8000 文字・具体的な試験の対象・最終の scope を確かめる（`CLAUDE.md` の「概ね 30 本」は上限、小さく切るのは目安）
- ゲートの増減と `.commandmate/` 配下は人だけが変える（既存）

## 3. 評価の時点と、既存の merge の手順への差分

既存の手順は、ワーカーの PR ごとに管理が CI green と scope を確かめて順に squash merge し、残りは BEHIND を往復する（`docs/parallel-development.md` §6.2・§6.3）。計測は PR ごとではなく **wave ごと**に窓口が流す。原則は **wave の統合候補を main に入れる前に同じ組で比べる**。どちらにするかと戻す責任は**所有者の判断 (b)**。

| 既存の手順 | merge 前の評価（判断 (b) ①）での差分 | merge 後の暫定採用（②）での差分 |
|---|---|---|
| PR が CI green になったら管理が順に merge する | **wave の PR が揃った時点で管理は merge を止める。** 統合候補は管理が作り（比較元の base に対象 PR を重ねた worktree）、比較元・候補の内容・対象 PR・検証の証跡を窓口へ渡す。同じ共通の原因を複数の PR に分けた wave でも、統合した内容で測る | 既定どおり merge する |
| merge が終わったら次の wave を dispatch する | 窓口が候補を計測し、独立レビュー（§1）の証跡と合わせて可否を返すまで merge しない。可なら、**確認した候補と実際に入れる内容の一致**を確かめてから merge する。途中で base や差分が変わったら、比較への影響を確認し、必要なレビューと計測を取り直す | **暫定採用**として次の dispatch を止める。窓口の計測で劣化の確認（`01` §4）のあと、戻す（revert の PR は窓口が起こし、人が merge）か追加の調査かを、窓口の提案と所有者の決定で決める |

- 計測待ちと候補待ちは `workspace/mem/README.md` の「いま」と、管理の `DONE` 行（「窓口の計測待ち」）で見える形にする。構造の直しは「前 20・後 20・回帰 30」（`01` §5）で、結果（指標・モードの件数・到達本数）を Issue のコメントに残す

## 4. 隔離（封と鍵）

- **ワーカーと CI は外部 API を呼ばず、鍵と環境ファイルを読まない。** この制約は依頼文と最初の追加の指示で届ける。worktree の baseline は環境ファイルへのリンクを張る（`CLAUDE.md`）ので、**鍵を持たないことを隔離の根拠にしない**
- 保留の組は、開発と受入の判定の直前まで封を保ち、最終候補を固定して 1 回で使い終わる。開発側には匿名の集計だけを返す口を用意する。人の確認は、所有者か実装に関与しない**人の採点担当**が実行後に行い、機械の判定と並べて報告する。AI の独立レビューを補助に使う場合も、人の確認の代替にはしない。結果を見て直したら新しい保留の組を封する。**担当と公開の範囲は所有者の判断 (d)**
- 回帰用は見てよいが、落ちの中身を調べない。調べた題材は開発用へ移して組の版を上げ、移動で落ちが消えたことを改善に数えない（`01` §1）

## 5. Hooks

本物の API を呼ぶ評価を Hooks・CI に入れない（費用・実行の責任・公開ログ）。Hooks に置くのは、**費用の掛からない検査**（合成の例・再生・規則の台帳の照合）と**計測待ちの通知**だけ。既存の採点の回帰（`regress.mjs`・`run-cases.mjs`）を CI に入れるなら、入力を固定し、許可した判定の差と照合して終了コードで失敗を返す試験に整えてから。

## 6. `CLAUDE.md` に足す文の案（1 か所。直すのは人）

「不変条件」の「プロダクト内の工場」の箇条の下に足す。本数や形式の詳細は方法論だけを正本にする。**足す時点**：方法論を人が読んで merge する文書 PR として追跡対象にし（`06` §1）、新しい worktree が正本を読める状態になってから。参照する版は、その PR の版に結び付ける。

```markdown
- **工場（`packages/factory`）の直し方は `workspace/mvp/m1/agent/methodology/` に従う。** 工場の変更は、実装前に共通の原因と観測外の反例を示し、コード・契約・入力から直す候補を検討する。意味の独立の点検と門を保つ。規則には理由と履歴を残す。wave の統合候補は実装に関与しないレビューと窓口の変更前後の評価を経てから merge し、確認されるまで次の wave へ進めない。ワーカーは API を呼ばず、封（保留の組）を読まない。Issue・scope・人の merge は既存の手順に従う
```
