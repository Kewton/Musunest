## 0. なぜ役割の違う組を持つか

落ちの中身を見て直した組は、その組に適応する。だから、**直しの根拠にする組**（読んでよい）、**壊していないかを数える組**（落ちを調べない）、**一般化を 1 回だけ確かめる組**（封）を分ける。受入の P1〜P10 は開発と受入の比較に使われ、独立した回帰用はまだ無い。保留の 15 題材は別に封がある。

## 1. 3 つの組

| 組 | 役割と読み方 | 今の資産 | 流すのに要るもの（§2） |
|---|---|---|---|
| **開発用** | 落ちをため、原因を調べ、合成の例の元にする。記録・納品物を読んでよい | P1〜P10（5 題材 × 2 書き方。**20 本流しても 20 題材ではない**） | 今の入口でよい |
| **回帰用** | 直しの前後で同じ組を数え、壊していないかを見る。落ちの中身は調べない。調べた題材は開発用へ移し、**組の版を上げて基準を測り直す**（見た題材で選んだ直しは、その組に適応するから）。**移動で落ちが比較から消えたことを改善に数えない。** 旧版で確認した劣化は台帳に残し、解消か受け入れの判断まで追う。新版は対象の機能・書き方・書けない範囲の対応を保つよう補充し、題材と採点のレビューを経てから基準を測り直す。旧版と新版の成績は、組の変更をまたぐ改善として比較しない | 無い。「語彙の穴」の組（`03-evaluation.md` §3）は流せる形の所在を確かめていない | 題材 ID・依頼文・採点の定義・書き方・書ける範囲を指定する入口。**最初の変更の前に基準を測る** |
| **保留用** | 開発と受入の判定の直前まで封を保ち、最終候補を固定して 1 回で使い終わる。開発側には匿名の集計だけを返す。人の確認は、所有者か実装に関与しない採点担当が機械の判定と並べる | 封をした 15 題材（Musunest-workspace。採点の定義の所在は未確認） | 匿名の集計だけを返す口（今の採点の道具は行ごとの失敗の鍵を標準出力へ出す） |
| 補助 | 採点表の正例・負例（`eval/cases/`・`regress.mjs`）、本物の応答の再生（`__fixtures__/`）、モードごとの合成の例 | あり | CI に入れるなら、固定の入力と許可した判定の差を照合して終了コードで失敗を返す形に整える（今の `regress.mjs` は差を表示するだけ） |

## 2. 新しい組を流すのに要るもの（前提の作業。`06` の実施計画に入れる）

前提を 2 つに分ける。**最初の Plan→Build の前後比較に必須のもの**（揃うまで正式な基準を測らない）と、**あとの切り分け・最終受入に要るもの**（必要になる時点までに作る）。全部を再開の前提にすると、再開までの距離を判断できない。

| 要るもの | 今 | 誰が | いつ |
|---|---|---|---|
| **評価セットの入口**（題材・書き方・対象範囲・採点定義を指定） | `run-agent.mjs` は固定の文書の P1〜P10 を読み、`score-agent.mjs` も P 番号 → 題材・書き方・書ける組の対応が固定。`run-cases.mjs` は `cases.json` を列挙する | 窓口（human-only。workspace の道具） | 必須 |
| **既存の採点器の分母の補正と、本数の照合** | 生成に失敗した本は要件数を持たず（`score-agent.mjs:24`）、静的 NG も持たない（`engine.mjs:186`）ので、充足率の分母に 0 を足す（`score-agent.mjs:43`）。同じ要件数の 2 本で 1 本が全充足・1 本が生成失敗なら、充足率は 100% になる。予算で止まる経路（`run-agent.mjs:147`）があり、採点は出来たディレクトリだけを集計する | 窓口 | 必須（§3） |
| **採点の定義と正例・負例** | 題材ごとの `subjects/<id>.json`。原文と了承後の二系統（決定⑥）。新しい組は、正例・負例と集計を API 不要の試験で確かめてから本物の計測に使う | 窓口の案 → Codex の独立のレビュー → 所有者 | 必須 |
| **比較条件の指紋**（§4） | `conditions.json` は commit・dirty・工場の dist・依頼文の SHA・子へ渡す引数まで（`run-agent.mjs:66-72`） | 窓口 | 必須 |
| **台本**（Plan の質問に、**質問 ID ではなく点検済みの事項**で答え、不明な問いは不明として扱う） | `--answers {}`（すべて推奨）なので、不要な質問の数しか測れない | 窓口 | 初期セットで扱う事項の分は必須。曖昧な依頼の組（`04-plan-agent.md` §9）の全体は後 |
| **匿名の集計の口** | 無い | 窓口 | 必須（回帰用に要る） |
| **確定した仕様から Build だけを流す口** | ライブラリ（`runGeneration`）は仕様を受け取るが、CLI と計測の道具に、仕様を読み込み、確認 SHA・版・条件を検査して渡す引数が無い。再利用する仕様は変更の前に固定する | ワーカー（CLI）＋窓口（計測の道具） | **後**。Plan と Build の切り分け（`04-plan-agent.md` §9）を始める時点までに。最初の比較を止めない |

- Build だけの比較は、締切と予算の適用の単位が Plan→Build と違う。**Plan→Build 全体の改善の証拠とは分けて報告する**。Plan の省略で減るのは本ごとの Plan の費用の分で、半額を保証しない

## 3. 指標と分母

- **合格の数は、凍結した外部の採点（v5）の PASS を基本にする。** 工場の `full`・`partial`・`none` は別に記録する。`full` が増えても、除外した要件や未点検の申告が増えただけのことがある
- Plan を通す組は、**原文の充足と了承後の充足を別に数える**（所有者の決定⑥）
- **要件の分母は、原文系・了承後系それぞれ採点定義から決め、生成失敗・静的 NG は充足 0 としてその分母に残す**（`03-evaluation.md` §4 の「失敗した本も分母に入れる」を充足率にも当てる）。**予定した本・実行した本・未実行の本を照合し、未実行が残る計測は「未完了」と表示して正式な比較基準にしない。** これらを含む正例・負例を API 不要で確かめ、前後は同じ集計の版で採点する。補正の前の計測の充足率は、この文書の比較に使わない
- 新しい組にも、静的チェック・挙げ漏れ・充足率・誤った申告・無い語彙・時間と費用の分母を**セットの定義に固定**する。書ける題材の率は、その対象の本数を分母にする（今の受入 50 本の分母は 30）
- F1（P3 の独立の点検）・P5 後の差分の点検・二系統の採点が整うまで、**自動の計測を成績の確定に使わない**（確定は所有者の決定⑤）

## 4. 前後比較の読み方

| 決まり | 理由 |
|---|---|
| **意図した変更以外の比較条件を固定する。** 題材・採点定義・モデル・effort・締切・予算の適用単位をそろえる。**実行と採点が参照する内容の指紋と、有効な adapter・モデルの構成を記録する**：工場と spec-engine の dist、生成に渡す文書（契約・語彙の意味・語彙の台帳。`cli.ts:486-495`）、採点定義と集計（`subjects/*.json`・`engine.mjs`・`score-agent.mjs`）、判定の口の構成（Jev を主に LLM を落とし先にするか、LLM だけか。`cli.ts:247-258`。環境で切り替わる）。鍵そのものは記録しない。**意図した変更の範囲を宣言し、それ以外の差があれば同じ条件の比較や基準の再利用として扱わない** | commit や dist を前後で同一にする条件ではない。同じコード・引数でも判定の構成が違えば別の条件で、変更の効果を分離できない |
| **対象のモードが 0 件なら「今回未観測」と書き、その段まで到達した本数を添える** | 0/20 でも区間の上限は 16% ある。停止が前の段へ移って未観測になることもある |
| **合格数の増減は探索の信号として扱い、固定の本数の差で雑音・改善を断定しない** | 同じ性能でも、10 パターン × 3 回の前後でどれかが 2 本減ることは珍しくない（独立・確率 1/2 なら約 69%）。固定の差を使うなら暫定の警報と明記し、比較の履歴がたまったら題材と条件ごとに見直す |
| **門の違反は即時に止める。それ以外の劣化の疑いは同じ条件で確認計測し、結果と不確かさを並べて次の wave の可否を決める** | 1 回の差で戻すと、戻す判断も雑音に乗る |
| **Wilson の区間は固定した組での実行のばらつきの参考として示す。同じ版の反復は任意の予備計測で、1 回の比較で普遍の閾値を決めない** | 50 本は既存の受入の本数であって、90% を保証する最小の本数ではない。得られるのは 10 個の小さな前後差で、別の題材・effort・版に同じ線を当てる根拠は無い。未知の題材への一般化は保留の組で確かめる |

## 5. 計測の単位と費用

| 単位 | 本数 | 使い方 |
|---|---|---|
| 診断（少数） | 3〜5 | 停止の経路を読み、観測と主因候補を台帳へ積む。本数だけで品質や一般性を確定しない |
| 構造の変更 1 wave の標準 | 開発用の**前 20・後 20**＋回帰用 **30** ＝ 70 | 予定本数まで流し切る（止まったら未完了）。直前の同じ条件の基準を再利用できるときだけ前 20 を省く |
| 別に見込むもの | 削る試験・確認計測・初回の基準・新しい組の基準 | wave 数と一緒に数え、回数と再利用の条件を決めてから予算を所有者へ出す |
