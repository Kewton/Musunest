# 03：正しい層で直す

> 状態：**採用 v3**（2026-10-12・所有者が採用）。構造の正本は `02-architecture.md`・`04-plan-agent.md`。構造を変える案（§3）は所有者の判断を経て正本へ反映する。コードの行は main `96a691d`。

## 0. なぜ下の候補から検討するか

プロンプトの規則は最も安く足せて、最も散らかる。コード・契約・入力の直しは効く範囲が広く、費用が下がり、規則が減る。だから候補を**安いほうではなく、効く範囲の広いほうから**検討し、上の段を選ぶときは「下の段で直せない理由」を Issue に書く。段は検討の目安であり、毎回すべての段の案を書く義務ではない。

## 1. 直しの候補（H1〜H7）

| 段 | 直し方 | 選ぶとき | 採らない理由として書けること |
|---|---|---|---|
| H1 | **コードで決める** | 上流の構造化出力・宣言・契約の文書から**決定的に**導ける。ただし「決定的」は組み立ての処理にだけ言え、意味の正しさは別に点検する（§2） | 原文の意味を読む必要がある（要件の文・質問の文・設計の選択・期待の値） |
| H2 | **持ち主を 1 つにして契約に載せる** | 同じ事実を複数の段が別々に推測している（§3）。参照する表現を 1 つにする | 意図した独立の点検である（その点検はコードで照合できる形に落とす。`02-architecture.md` §1.2） |
| H3 | **段に要る情報を渡す** | 契約にはあるが入力に無い。前回の失敗の中身を次の試行に渡していない | 渡すと独立性を壊す（期待の値・合否。R2-1） |
| H4 | **道具・検査の返り値と行き先を直す** | 落ちは検出しているが、直せる段に届かない・分類が粗い・同じ要求を繰り返す | 返り値を「通す」側に変えることになる（門を緩める） |
| H5 | **段を分ける・まとめる・順を変える** | 1 段が複数の判断を背負う。順番のせいで前の段の結果を知れない | 呼び出しと費用が増える（見積もりを書く） |
| H6 | **判定の口（Jev）に閉じた問いとして移す** | 答えが閉じた集合で、確信度で道を分けられる | H1 で決められる。文を作る・計算する・合否や権限を決める問いである（`05-judge-model.md` §3）。判定の口の答えは**助言**であり、門の省略を決めさせない |
| H7 | **プロンプトを原則と理由で直す** | H1〜H6 で直らない「規則が無い・曖昧・矛盾」 | — （`04` の条件を満たす） |

## 2. 不変条件（どの段を選んでも）

- **特例を作らない。** 特定の題材・値・名前・構造を名指しする規則・分岐、1 本の落ちだけを根拠にする規則、同じ種類の他の値に効かない分岐。種類の全部に掛かる文は特例ではない。門を fail-closed 側に強める検査は、1 本が根拠でも入れてよい（コードで）
- **門を緩めない。** 通す側に変える・未解決や未実行を 0 に数える・usage 不明の予約を戻す・候補の件数で結び付けを選ぶ、は禁止。緩めるしかないなら所有者の判断に回す（現在の門を迂回する許可ではない）
- **意味の独立の点検を残す。** 持ち主を 1 つにしても、要件への必要性と期待の意味は確定した仕様から独立に点検する。誤った所属・選択肢の欠落や意味の逆転・対象や default や checks の誤りを入れた設計が `full` にならないことを、構造の直しの完了条件にする。プロンプト・試験・誤りの文に受入の題材の言葉を入れない（`04` §1・`05` §1）
