# dev の 10 ms の壁は「継続して超えたときだけ」効くのか（Issue #152）

> 測った日：**2026-09-18（UTC）**。宛先は **dev（アカウント①）** の**計測用インスタンス**。
> staging は既に Workers Paid で `limits` を設定していないので、Free の壁の再現には使わない（[`../m0/06-plan-and-limits.md`](../m0/06-plan-and-limits.md) §5）。
> **URL・ホスト名・バケット名・Account ID・資格情報は、この文書にもログにも出さない。**

---

## 0. 結論（先に）

| 判定 | 結果 | 根拠 |
|---|---|---|
| **仮説**「10 ms の壁は、1 回でも超えたら落ちるのではなく、**継続して**超えたときに落ちる」 | **確定しなかった（否定もされなかった）** | 「たまに」も「継続して」も `exceededResources` は **0 件**で、応答も全回 2xx だった（§4・§5） |
| dev の data-api に `limits.cpu_ms: 10` が配備されていたこと | **確かめた** | Worker の設定を Cloudflare の API で読むと `{"cpu_ms":10}`（配備直後）。staging の同じ欄は `null` |
| 10 ms を大きく超える CPU 時間が記録されたこと | **確かめた** | data-api の `max.cpuTime` は「たまに」**36.03 ms**・「継続して」**33.55 ms**（期間の最大は 57.03 ms。§4） |
| 片付け | 済み | 行は 0（§8） |
| `limits` を外して元に戻したこと | 済み | 外して dev へ配備し直し、設定が `null` に戻ったことを確かめた（§9） |

- **仮説は確かめられなかった。** 10 ms の上限を明示的に設定した dev で、**20 回を 1 窓**でも **200 回を間隔を空けずに 1 窓**でも、
  上限超過（`exceededResources`）は 1 件も出ず、応答は**全回 2xx**だった。**「片方だけ落ちる」という仮説の形にはならなかった。**
- **「否定された」とも言えない。** 落ちなかった理由は切り分けていない（§6）。**分からないことを分かったように書かない。**
  この実験で言えるのは「**10 ms を数倍超える記録が残っても、この 2 通りの当て方ではエラーにならなかった**」ところまでである。
- `exceededResources` は、この実験では**「落ちたか」の判定に使えることを確かめられていない**。§6 に、その他の候補を挙げる。

## 1. 何を測ったか（判定の線）

Issue #152 の背景はこうである。#111 の実測で、staging の `/api` の経路で **data-api 単体の CPU 時間の最大が 60.60 ms** に達したのに、
同じ期間の `exceededResources` は **0 件**だった（[`measurements.md`](./measurements.md) §0・§9）。Free の上限は 1 リクエストあたり 10 ms である。

Cloudflare の設定の文書（wrangler の `limits.cpu_ms`）は、上限を「たまに」超えるぶんには isolate に融通があり、
「継続的に」当たり始めると実行が終了される、と読める。**仮説：10 ms の壁は「1 回でも超えたら落ちる」ではなく「継続して超えたら落ちる」。**

| 当て方 | 送る回数 | 「落ちた」の判定 |
|---|---|---|
| **たまに**（#111 と同じ当て方） | **20 回を 1 窓**（先に 5 回温めて 60 秒空ける） | 窓のあとの `exceededResources` が **1 件以上**なら落ちた。応答が非 2xx でも落ちた |
| **継続して** | **200 回を間隔を空けずに 1 窓**（同じく 5 回温めて 60 秒空ける） | 同上 |

**「落ちたか」は 2 つで見る。** `exceededResources`（`free-tier-report.ts`）と、**応答の HTTP ステータス**である。
後者は「エラーが利用者にどう見えるか」を知るためである（Issue #152 の `## やること` 4）。

- **確かめたい仮説**：「たまに」で落ちず「継続して」で落ちる → **確定**
- **どちらでも落ちない** → **否定されていない**（別の理由が残る）→ **この実測がこれ**
- 上限を設定できない（wrangler が受け付けない）・資格情報が足りない → **その場で止めて人に返す**

## 2. 測り方

**新しい計測の道具を作らない。** 既存の 2 本を再利用する（`06` §5「先に安い手を試す」）。

- 重い読み取りを当てる側 … `infra/scripts/measure-free-tier.ts` の **`--api` モード**（#111 で `/api` の経路に広げてある）
- `exceededResources` を読む側 … `infra/scripts/free-tier-report.ts`（**読み取りだけ**）

`--api` モードに、この実測のための 2 つを足した（Issue #152。**送る・待つ・読むの本体は変えていない**）。

- `--env dev|staging` … 既定は staging（#111 と同じ）。**dev は、上限を自分で設定して Free の壁を再現するときに使う**
- `--max-requests <n>` … 1 経路・1 規模あたりに送る回数の上限（既定 50 = Issue #25 で承認された枠）。
  「継続して」の 200 回は **`--max-requests 205` と明示して**送った。**経路を合算して緩めるのとは別である**

```bash
# 条件：宛先は dev（アカウント①）。5 回温め → 60 秒空けて → 1 窓で測る（measurements.md §2 と同じ作法）
pnpm exec tsx --env-file=.env infra/scripts/measure-free-tier.ts --api --env dev --instance m12-cpu-limit \
  --sizes 200 --routes memberList --warm 5 --count 20                       # たまに（20 回）

pnpm exec tsx --env-file=.env infra/scripts/measure-free-tier.ts --api --env dev --instance m12-cpu-limit \
  --sizes 200 --routes memberList --warm 5 --count 200 --max-requests 205   # 継続して（200 回）

# それぞれの前後で、上限超過を別に読む（Issue #152 の `## やること` 4）
pnpm exec tsx --env-file=.env infra/scripts/free-tier-report.ts --account 1
```

- 経路は **`memberList`**（200 件の member 集計。`measurements.md` §4 で data-api が最も重かった経路。60.60 ms）
- 1 回の実測で送るのは、温め 5 ＋ 本測定（20 または 200）。**応答が非 2xx なら、その場で止める**（そのときの HTTP ステータスを出す）
- 準備（メンバー 3・支出 200）と片付けは**計測の窓の外**に置く。片付けは #109 の削除の操作（支出 → メンバーの順）
- CPU 時間の正は Workers Analytics の `max.cpuTime`（Worker 別）。応答時間では代用しない
- Analytics は本測定の窓だけを、**2 回続けて同じ値**になり、**Worker ごとの回数が送った数くらい**になったら反映済みとみなす

## 5. 判定

| 問い | 判定 | 根拠 |
|---|---|---|
| 仮説（継続して超えたときだけ効く）は**確定したか** | **確定しなかった** | 「たまに」も「継続して」も落ちなかった（§4）。片方だけ落ちる形にならなかった |
| 仮説は**否定されたか** | **否定されなかった** | 落ちなかった理由を切り分けていない（§6）。「継続」の定義・`exceededResources` の意味を確かめきれていない |
| **分からなかった**のか | **分からなかった**（確かめられなかった） | 10 ms を 3 倍以上超える記録が残っても、この 2 通りの当て方ではエラーが出なかった。**その理由はこの実測からは決まらない** |

- **確定：`limits.cpu_ms` に 10 を設定して wrangler は受け付けた**（下限で弾かれなかった。回避策は要らなかった）。
- **確定：dev の data-api は 10 ms の上限つきで動いていた**（Worker の設定を API で読んで確認）。
- **確定：10 ms を大きく超える CPU 時間が記録された**（36.03・33.55 ms。期間の最大 57.03 ms）。
- **確定：そのどちらの窓でも `exceededResources` は 0 件で、応答は全回 2xx だった。**
- **未確定：10 ms の壁が「継続」で効くかどうか。** 少なくとも**この 2 通りの当て方の範囲では効かなかった**。
- **未確定：`exceededResources` が、この条件で「CPU 上限で落ちた」を写せる欄なのかどうか。**

**したがって、`06` の F-1 に書く結論は「確定しなかった（仮説は否定されてもいない）」である。**
「たまに／継続して」の違いで説明できた、とは書けない。

## 6. 読み方と、残る不確かさ

- **「落ちなかった」は「壁が無い」ではない。** 確かめられたのは、10 ms の上限を明示的に設定した dev で、
  **20 回・200 回のどちらの当て方でもエラーが出なかった**ことだけである。**何回・何秒続ければ「継続」になるのかは測っていない。**
  Issue #152 の止まって人に返す条件（「200 回を超えて投げないと結論が出ないと判断したとき」）に当たるかどうかは、
  **投げる回数を増やす前に人へ返す**と決めてある。この実測では 200 回で止めた（§7 にその旨を書く）。
- **`exceededResources` の意味が違う可能性がある**（Issue #152 の `## やること` 5 が挙げている候補）。
  Free のときに「60 ms でも 0 件」だったのと同じ欄を、Paid + 明示 10 ms でも見ている。
  **この欄が CPU 上限の終了を写すのかを、この実測は確かめていない。** 一次情報の
  「`exceededResources` は CPU 時間のほか起動時間・Free の上限でも付く」も、**「明示した `cpu_ms` の超過で付く」とは書いていない。**
- **「継続」の単位が分からない。** 200 回は**逐次**（1 回ずつ応答を待つ）で、47 秒に収まった。
  同時実行・並列・もっと長い時間窓での継続は測っていない。**isolate に融通が残っていた可能性**は残る。
- **CPU 時間は Analytics の推定値である。** 全窓にサンプリングがあった（回数は推定値、`max` は取りこぼし得る）。
  ただし 36.03・33.55 ms は 10 ms から遠く、**揺れでは説明できない**。
- **窓の max が「他所の 1 件」である可能性**は、回数の帯（送った数の半分〜倍）でしか見ていない。
  とくに「継続して」は data-api の回数が 239 回（送った 200 回より多い）で、**サンプリングの重みか、他の通信の混入**である。
- **`errors` は 0 だった。** これは「実行が終了されなかった」ことと整合する（終了されれば 5xx か errors が載るはずである）。
  ただし **`errors` と `exceededResources` の関係も確かめていない。**

## 9. 元に戻したこと（`limits` を外した）

Issue #152 の `## やること` 6。**実験のための一時的な設定を残さない。**

1. `packages/data-api/wrangler.jsonc` の `env.dev` から **`"limits": { "cpu_ms": 10 }` を外した**（`env.staging`・`env.production` は触っていない）
2. dev へ配備し直した：`deploy-worker.ts --env dev --target data-api --sha <HEAD>`
3. **Worker の設定を API で読んで、`limits` が `null` に戻ったことを確かめた**（staging も `null`）
4. dev の貫通スモークが全層 ok であることを確かめた（host → gateway → data_api → d1 / r2 / do）
5. `packages/data-api/src/index.test.ts` は「**`limits` はどの環境にも無い**」を確かめる形にしてある（この実測のあとの状態が正）

> dev に配備した host・gateway・data-api は、**この実測のために現在のツリーから配ったものである**（配備済みが古かったため）。
> これは戻す対象ではない（`/api` の経路を通すのに要った）。
