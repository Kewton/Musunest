## 2. 測り方

`infra/scripts/measure-free-tier.ts` の **`--api` モード**（この Issue で足した）を、手元から staging へ向けて回した。

```bash
pnpm exec tsx --env-file=.env infra/scripts/measure-free-tier.ts --api --instance m12-cpu-warikan
```

- 経路は4つ、規模は3つ。**各経路・各規模を個別に、5 回温めて → 60 秒空けて → 20 回測る**（`06` §8 の再測と同じ。Q15）。温めの窓と本測定の窓を分ける
- **1 回の実測は 25 回（温め 5 ＋ 本測定 20）で、既存の上限 50 回の内側**。**全経路を合算して上限を緩めない**（各経路・各規模が独立した「1 回の実測」である）
- 準備（データ生成）と片付けは**計測の窓の外**に置く。本測定の窓のあとは、窓の余白（前後 2 秒）より長く空けてから片付ける
- **CPU 時間は応答時間で代用しない。** Workers Analytics の `workersInvocationsAdaptive` を **Worker 別**（`dimensions.scriptName`）に読み、`max.cpuTime`（マイクロ秒）を ms に揃えて使う
- 本測定の窓だけをまとめて1回の GraphQL で読み、**2 回続けて同じ値**になり、**3 Worker の回数が送った数くらい（半分〜倍）**になったら反映済みとみなす。窓ごとに判定し、落ち着かなかった窓だけを判断不能にする
- **判断不能に落とす条件**：Analytics を読めない（権限不足を含む）・窓の行が無い・名前が `__unknown__`・回数が送った数と合わない（他の通信の混入・反映不足）・反映を待ちきれない・過去 7 日分が確認できない（P-1）。**未測定を 0 や成功として記録しない**

再測のときに差し替えられる形にしてある（時計・sleep・HTTP・Analytics・期間レポートを io から受ける）。unit は fake で、5 回→60 秒→20 回・窓の分離・応答の失敗で止まること・規模 2/20/200 の準備と片付けの順・P-7/P-1 の境界を確かめる（`infra/scripts/measure-free-tier.test.ts`・`infra/scripts/api-measure-fixture.test.ts`）。

## 6. 静的な上限の提案（**確定しない**。根拠つき。M1.5 に渡す）

`03` §5.1 の「無償枠の目安（entity・集計・式の数が上限の内か）」の上限値を、この実測から**提案まで**出す。**確定は M1.5**（Q18-10）。

**根拠になった計測条件**

- 見本 1 種（`warikan`）。**静的な数は、entity 2・項目 5・view 3・action 5・validation 2・computed 6（式 3・集計 2・精算 1）で固定**（§3）
- 動かしたのは **`expense` の保存レコード数だけ**（2・20・200）。member は 3 人で固定。同じ 2 支出の組を繰り返しただけ
- 測り方は §2（5 回温め → 60 秒 → 20 回、窓ごと、Worker 別の `max.cpuTime`）

**提案（実測と対応づけて）**

1. **上限の変数は「保存レコード数」と「member 数」である。** 実測で CPU を動かしたのはこれだけで、`spec` は件数に依らなかった（2.00〜2.88 ms）。だから目安は「1 インスタンスの `expense` の件数」と「member の人数」で表す。
2. **data-api の集計・精算 3 経路は、実測点の範囲で単調に増えた。** 実測の傾きは **expense 1 件あたり概ね 0.1〜0.3 ms**（expenseList ≈0.14・memberList ≈0.27・settlement ≈0.10 ms/件）。
3. **「何件までなら安全」という上限を、今の実装からは出さない。** 落ち着いた状態の単体 7 ms の線に対して、**20 件ですでに 3 経路が超えている**（expenseList 12.99・memberList 7.29・settlement 7.64 ms）。実測点（2・20・200）から逆算すると、7 ms 以下の件数は経路ごとに **0〜1 桁台**（memberList ≈1.6 件、expenseList ≈28 件、settlement は 2 件でも超過）で、**幅がありすぎて 1 つの数に決められない**。
4. **だから M1.5 に渡すのは「上限値」ではなく「集計・精算の経路は、20 件でも 7 ms を割るために実装の見直しが要る」という事実**である。上限は、見直しのあとの再測で決める（`03` §6 の「無償枠の目安の上限値」を M1.5 に置いた理由がこれ）。
5. 参考として、`entity`・`集計`・`式`の**数の**上限を、この見本の 1 点（2・2・3）から**決めない**。数は変えていないので、上限の根拠になる計測が無い。

**測れていない範囲（この実測で上限を確定できない理由）**

- **entity の数・集計の数・式の数・参照の深さ（AST の深さ）を変えたときの CPU**（今回は固定。1 点しか無い）
- **member の人数**（今回は 3 人で固定）と、**参照 list（`participants`）の長さ**
- **もっと細かい件数の刻み**（2・20・200 の 3 点だけ。7 ms の線をまたぐ件数は測っていない）
- **経路を同時に叩いたとき**（今回は 1 経路ずつ。同時実行・キャッシュの効きは見ていない）
- **サンプリングの無い状態**（12 窓すべてでサンプリングがあった。`max` は取りこぼし得る）
- **コールドスタートと定常の分離**（60 秒の温め→本測定の間で isolate が落ちた場合、`max` に起動の CPU が混ざり得る。分離していない）

## 9. 読み方と、残る不確かさ

- **これは「落ち着いた状態」の 1 回の実測である。** 経路×規模ごとに 1 窓（本測定 20 回）だけ。**繰り返して中央値を取ってはいない**。7 ms の線の近く（6.5〜7.5 ms）の経路（20 件の memberList 7.29・settlement 7.64）は、もう一度測ると線をまたぐ可能性がある。**7 ms から遠い値（11.51・12.99・30.25・32.12・60.60）は、揺れでは説明できない**
- **60 秒の温め→本測定の間で isolate が落ちると、最初の 1 回に起動の CPU が乗り得る。** 今回はその分離をしていない（`max` は窓の中の最大 1 件）。M0 の §8 と同じ測り方である
- **サンプリングが全窓にあった。** 回数は推定値で、`max` は取りこぼし得る（逆に、観測された `max` は実在した 1 件の値である）。**200 件の memberList 60.60 ms は 10 ms の上限を大きく超えているのに `exceededResources` が 0 件**なのは、`06` §7.1 の「上限未満の余りを繰り越す仕組み」で説明され得るが、**切り分けていない**
- **他の通信の混入は、回数の帯（送った数の半分〜倍）でしか見ていない。** 窓の中の `max` が「他所の遅い 1 件」である可能性は、回数が合っていても残る
- **P-1 の 7 日は、この実測の 20 回とは別に読んだ。** 実測そのもの（20 回の窓）で 0 件だったことは P-1 の根拠にしていない
