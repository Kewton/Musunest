# M1.1〜M1.4 での意味（community.app-spec/v0.2-draft）

> 宣言の形だけでは 1 つに決まらない振る舞いを、この語彙について決める（`workspace/mvp/m1/04-spec-evolution.md` §1.1、`00-open-questions.md` Q3）。
> **M1.1 の語彙は v0.1 と同じ**で、**M1.2 で参照（`ref`）・検査の文言（`message`）・entity をまたぐ集計（`aggregate` の `sum`・`count`）・精算（`settle`）・一覧の種類（`table`・`settlement`）を足した**（印を付けてある）。
> **M1.3 で選択肢（`enum`）・既定値（`default`）、日付（`date`）・「今日」（`today()`）、決まった値への書き換え（`set`）とボタンを出す条件（`when`）、ボード（`board`）と強調（`highlight`）、一覧（`list`）と絞り込み（`filters`）、**表示名（`label`）**を足した**（印を付けてある）。
> **M1.4 でアプリ全体の集計（`scope`）と平均（`avg`）、期間の条件（`within`）、見出しごとの集計（`groupBy`・`groups`）を足した**（#177・#178・#179。印を付けてある）。
> **ここに無い振る舞いは、まだ決めていない**（末尾の「まだ決めていないこと」）。
> 語彙の一覧は [`../vocabulary.yaml`](../vocabulary.yaml)、型は [`../src/spec.ts`](../src/spec.ts) にある。見本は [`../samples/expense-log/`](../samples/expense-log/)、[`../samples/warikan/`](../samples/warikan/)、[`../samples/task-board/`](../samples/task-board/)、[`../samples/dashboard/`](../samples/dashboard/)。
> 節の見出し（`### entity` など）は台帳の `semantics` 欄から参照される。見出しの名前を変えるときは台帳も直す（unit テストが突き合わせる）。

## 宣言の全体

- 欄は v0.1 と同じ 7 つ（`entities`・`views`・`actions`・`validations`・`computed`・`permissions`・`minIdentity`）を横に並べる。**7 つとも書く。** 中身が無ければ `[]` と書く
- 知らない欄・知らないキーは書けない（語彙は閉じている）。`required` など、まだ入っていない語彙は書けない（`kind`・`type` は M1.2 で、`label` は M1.3 で入った。「label」の節）
- 名前（entity・項目・検査・計算・一覧・操作）は、英字で始まる英数字（`^[A-Za-z][A-Za-z0-9]*$`）。式の中でそのまま名前として読むため
- 名前の重なり：entity の名前は宣言の中で 1 つずつ。項目と計算の名前は、同じ entity の中で重ならない。検査・一覧・操作の名前は、それぞれの欄の中で 1 つずつ
- `id`・`createdAt`・`updatedAt` は店頭が付ける値なので、項目と計算の名前に使えない（`02-l2-spec-examples.md` §1）

## データ層

### entity

- 記録するもの。`fields` に「項目名: 型」を並べる。書いた順が、一覧の列の順になる
- **M1.1 の項目はすべて必須である**（`required` の語彙がまだ無い）。入力に項目が無い・`null` のときは保存しない
  ——ただし、**選択肢（`enum`）の項目に既定値（`default`）があるときだけは、キーそのものが無ければ既定値を入れる**（M1.3。「enum」「default」の節）
- 保存するとき、店頭が `id` と `createdAt` を付ける。データは 1 インスタンス 1 つの Durable Object に置く（D1 には置かない）

### string

- JSON の文字列。空の文字列も 1 つの値として受け取る
- **式の中では、文字列の定数を二重引用符で書ける**（M1.3。`status == "done"`）。線引きは 3 つある
  - **二重引用符だけ。エスケープは無い**（`\n` も `\"` も書けない）。`"` を含む文字列は書けない
  - **使えるのは `==` と `!=` の比較だけ。** `+` で繋げない（`LOGIC_OPERAND_TYPE_MISMATCH`）
  - **`enum` の項目と比べる定数は、`options` のキーでなければならない**（「enum」の節）

### number

- JSON の数。**有限の数だけを受け取る**（`1e400` のように読むと無限大になる値は受け取らない）。整数に限らない
- 端数の扱い（1 円未満をどうするか）は M1.1 では決めない。M1.2 の精算で決める（Q13）。採点のシナリオは割り切れる値だけを使う

### list

- 文字列の並び。**空の並びと、同じ文字列が 2 回ある並びは受け取らない**。要素が文字列でなければ受け取らない
- 並びの順は、入力の順のまま保存する
- `of: <entity>` を付けると、**参照の並び**になる（`list of`。M1.2）。要素は参照先のレコードの ID で、
  空と重複を許さないこと、入力の順のまま保存することは文字列の並びと同じである。「ref」の節も見ること

### ref

- ほかの entity のレコード **1 件**を、その **ID** で指す（M1.2）。宣言では `{type: ref, to: <entity>}` と書く
- 値は**空でない文字列**（参照先のレコードの ID）である。空文字は ID にならないので受け取らない
- **名前ではなく ID で指す。** 名前が同じメンバーが 2 人いても、ID で区別する
- 参照先は、**同じインスタンス**（同じ Durable Object）のレコードである。別インスタンスの ID は存在しない
- 検査は二段である
  1. **宣言の検査（静的チェック）**：`to`・`of` の entity が宣言に実在するか。無ければ `DATA_REF_TARGET_NOT_FOUND`
  2. **保存の検査（data-api）**：入力の ID が、同じインスタンスの参照先のレコードに実在するか。
     無ければ `INPUT_REJECTED`（422）にして、**通らなかった項目の名前**を返し、保存しない
- 参照されているレコードを消せるかは Q13 で決めた（消せない）。実装は参照の削除を扱う語彙（M1.2 の後半）で行う
- 画面では、`ref` は参照先のレコードの**単一選択**、参照の並びは**複数選択**にする。
  **送るのは ID で、見せるのは名前である**（名前は、参照先の先頭の `string` の項目を使う）。
  候補が 0 件のときも**架空の ID を作らない**（先に登録してもらう。守りはサーバ側）

### enum

- 決まった選択肢のうちの **1 つ**を持つ項目（M1.3）。宣言では `{type: enum, options: {<キー>: <表示名>, …}}` と書く
- `options` は**保存される値（キー）と、画面に出す表示名の対**である
  - **キーは 1 つ以上書く。重複させない**（保存される値が重なると、区別が付かなくなる）
  - キーを書いた順が、**画面に出す選択肢の順**である（M1.3 のボードの列はこの順に並ぶ）
  - 表示名は空でない文字列である。**保存されるのは表示名ではなくキーである**
- 値は**文字列（キー）**である。式の中では `ref` の ID と同じく文字列として読む
- **式の中で、文字列の定数と比べられる**（M1.3。`status == "done"`）。比べる定数は `options` の
  キーでなければならず、キーに無ければ静的チェックが `LOGIC_ENUM_KEY_NOT_FOUND` で断る
  （`status == "todu"` の打ち間違いは、動かす前に止まる）
- **保存の検査（data-api）**：受け取るのは `options` のキーだけである。宣言に無い値は
  `INPUT_REJECTED`（422）にして、**通らなかった項目の名前**を返し、保存しない
  - **画面が選択肢を絞ることは守りではない。** 断るのは data-api だけである（`03` §2.2、`CLAUDE.md` の不変条件）
  - 空文字・数・並び・`null` も受け取らない（キーではないからである）。既定値への読み替えもしない（「default」の節）
- **宣言の検査（静的チェック）**：`options` が空なら `DATA_FIELD_ENUM_OPTIONS_EMPTY`、
  キーが重複すれば `DATA_FIELD_ENUM_OPTION_KEY_DUPLICATE`、`default` がキーに無ければ
  `DATA_FIELD_ENUM_DEFAULT_NOT_IN_OPTIONS`（「default」の節）
- 画面では**単一選択**（`<select>`）にする。**見せるのは表示名で、送るのはキーである。**

### default

- **未入力のときに、保存の時点で入れるキー**である（M1.3）。`options` のキーのどれかを書く。
  書かなければ既定値は無い（未入力のまま型の検査に掛かる。「entity」の節）
- 静的チェックは、`default` が `options` のキーのどれでもなければ `DATA_FIELD_ENUM_DEFAULT_NOT_IN_OPTIONS` で断る
- **入れるのは data-api である**（保存の時点）。画面が項目を送ってこなくても（キーそのものが無くても）入る
  - 入れるのは**保存する値だけ**である。入力そのものは書き換えない
  - **送られてきた値がキーでなければ、既定値に読み替えず `INPUT_REJECTED` にする**（黙って別の値にしない）
  - `null` は「送られた値」なので、既定値に読み替えない（型の検査で断る）
- **既定値が無ければ未入力のままである。** M1.1 の項目はすべて必須なので、`INPUT_REJECTED`（422）になる
- 保存の時点で入れるので、`create` と `update`（全項目の置換）の**どちらでも同じ**である（「update」の節）
- 画面は、既定値を**最初から選んでおく**のが親切である（未入力を空文字で送ると既定値が入らないため）。
  ただしそれは入力補助であって守りではない——守りは data-api 側にある

### date

- 日付（M1.3）。**保存する形は `YYYY-MM-DD` の文字列**である（例 `2026-09-15`）。時刻は持たない
- **Data API が唯一の権限強制点である**（`CLAUDE.md` の不変条件）——`YYYY-MM-DD` の形でない値は、
  入力の型の検査（data-api）が `INPUT_REJECTED`（422）にして、**保存しない**
  - **画面の入力欄が形を整えることは守りではない。** 断るのは data-api だけである（`03` §2.2）
- M1.1 の項目はすべて必須である（「entity」の節）。画面は日付の欄を空のまま送れるが、
  空文字は `YYYY-MM-DD` の形ではないので、data-api が型の検査で断る
- 式の中では `date` の型として読む。**日付どうしの比較**（`<` `<=` `>` `>=` `==` `!=`）が書ける。
  比べるのは `YYYY-MM-DD` の文字列である（桁数が同じなので、辞書の順が暦の順と一致する）
- **`date` と `number` の比較は書けない。** 静的チェックが `LOGIC_OPERAND_TYPE_MISMATCH` で断る。
  数の計算（`+` `-` `*` `/`）にも使えない
- 「今日」は `today()` である（「today」の節）。**日付の定数はまだ書けない**
- **見るのは形だけである**（`2026-02-30` のように暦に無い日も、形が合えば受け取る）。
  暦として正しいかまで断るかは、必要になったときに決める（末尾の「まだ決めていないこと」）
- 画面では日付の入力欄（1 つの日付）にする。**送るのは `YYYY-MM-DD` の文字列である**

### message

- 検査（`validation`）に付ける、**保存できない理由の文言**（M1.2）。任意である
- 付けるときは**空でない文字列**で書く（並び・写像・空は `SHAPE_VALIDATION_MESSAGE_INVALID`）
- 断ったときの応答は、**検査の名前の並び**（`validations`。宣言の順）と、その名前に対応する
  **文言の並び**（`validationMessages`。同じ並びで、文言の無い検査は `null`）を返す
- 文言を 1 つも宣言していない宣言（M1.1 の見本）では、応答に `validationMessages` を**載せない**。
  画面は検査の名前で識別する（#102 の約束を変えない）
- 画面は文言を**テキストとして**表示する（HTML として解釈させない）

## ロジック層

### validation

- 保存してよい条件。式は真偽になる（比べる演算子で終わる）
- 参照できるのは、同じ entity の項目と計算の名前
- 入力の検査は data-api が行い、次の順で進める。**どこかで断ったら保存しない**
  1. 型の検査：項目の過不足と、各項目の型。通らない項目を**すべて**返す（順は問わない）。ここで断ったら、検査の式は評価しない
  2. 計算：その入力で計算の値を出す
  3. 検査の式：**宣言の順にすべて評価し**、真にならなかった検査の名前を宣言の順に返す
- 式の途中で有限の数でなくなったら（0 で割るなど）、その検査は通らなかったものとする
- 断ったときに返すのは、項目の名前と検査の名前である。**検査が文言（`message`）を持てば、その文言も返す**
  （「message」の節。文言の無い検査は、従来どおり検査の名前で識別する）

### computed

- 計算は、**式（`expression`）と集計（`aggregate`）のどちらか一方**である（M1.2。同時に書けない）
- 式の計算は、同じ entity の中の計算（v0.1 の `reference_scope: same_entity`）。参照できるのは、同じ entity の項目とほかの計算の名前だけ。`budget.limit` のような `.` を使った参照は書けない。**別の entity を式から自由に読むことはできない**（集計は「aggregate」の節でだけ扱う）
- 計算どうしの参照は、依存の順に評価する（v0.1 の `evaluation_order: topological`）。**循環は書けない**（集計をまたぐ循環も `LOGIC_COMPUTED_CYCLE`）
- `type` は `number` と、**M1.3 で足した `boolean`**、**M1.4 で足した `groups`** である。式の値の型と一致しなければならない
  - **`boolean` の計算は、ボードの強調（`highlight`）が指すためだけに使う。** 一覧の列には出さない
    （一覧の応答の `computed` の並びにも入らない）。集計（`aggregate`）と精算（`settle`）は数を返すので、
    `boolean` を書けるのは式（`expression`）の計算だけである（「board」の節）
  - **`groups` は、見出しごとの集計（`groupBy`）の結果（「見出しと値」の組の並び）である。** これも
    一覧の列には出さない（`boolean` と同じ扱い。グラフの部品が指すためだけに使う。「groups」の節）
- 計算の値は保存しない。一覧を返すときに data-api が計算する。**画面は式を評価しない**
- 式の途中で有限の数でなくなったら（0 で割るなど）、その計算の値は `null` とする。**画面は `null` を「—」で見せ、0 と区別する**（空欄にも 0 にも読み替えない）
- 式に書けるもの
  - 数の定数（`0`・`1.5`）、項目と計算の名前、かっこ
  - 数どうしの計算 `+` `-` `*` `/`（結果は数）と、符号の `-`
  - 数どうしの比較 `>` `>=` `<` `<=` `==` `!=`（結果は真偽。検査の式と `when` の式でだけ使う）
  - 日付どうしの比較 `>` `>=` `<` `<=` `==` `!=`（結果は真偽。M1.3）。比べられるのは `date` の項目と
    `today()` だけで、**`date` と `number` を混ぜると `LOGIC_OPERAND_TYPE_MISMATCH`** である
  - 文字列の定数（`"done"`。M1.3）と、文字列どうしの比較 `==` `!=`（結果は真偽）。
    **`+` で繋げない**（「string」の節）。`enum` の項目と比べる定数は `options` のキーである（「enum」の節）
  - 店頭が用意した関数 `min`・`max`・`len`・`today` だけ。ほかの関数（`round` など）は書けない
  - `and`・`or`・`not`・`null` は書けない

### aggregate

- 「同じインスタンスの、別の entity のレコード」をまとめて 1 つの値にする計算（M1.2）。`computed` の 1 つとして書き、`expression` と**どちらか一方**だけを持つ
- 集計の元にするレコードは、**同じインスタンス**（同じ Durable Object）にあるものだけである。別インスタンスのレコードは見えない（「ref」の節と同じ）
- 集計の元の指定は 3 つである（`sum`・`count`・`avg`。**同時には書けない**）。`where` で対象を絞る
- `where` に書けるのは、**集計元の項目と `this` の比較**だけである。`this` は**出力先の entity の、今のレコードの ID** である
  - 参照（`ref`）の一致：`where: { payer: this }`（`payer` が `this` を指す行だけ）
  - 参照の並び（`list of`）の包含：`where: { participants: { contains: this } }`（`participants` が `this` を含む行だけ）
  - `where` の項目は、**出力先の entity を指す参照**（一致）か**その参照の並び**（包含）でなければならない。別の entity を指す参照・参照でない項目・`contains` と参照の取り違えは `LOGIC_AGGREGATE_WHERE_TYPE_MISMATCH`
- 対象は**1 行につき 1 回**だけ数える（重複して数えない）
- 集計は、**行ごとの計算 → 集計 → 集計を参照する計算**の順に解く。宣言の並びには依らない（「computed」の節）
- **`scope: app` を書けば、アプリ全体で 1 つの集計になる**（M1.4。Issue #177）。出力先のレコードが無いので、`where` に `this` は書けない（「scope」の節）
- 期間の条件（`within`）は M1.4 の #178 で足した（「within」の節）。**見出しごとに分ける `groupBy` は M1.4 の #179 で足した**（「groupby」「groups」の節）
- 宣言の検査は、集計元の entity・項目・計算の実在（`LOGIC_AGGREGATE_TARGET_NOT_FOUND`）、`sum`・`avg` の対象が数であること（`LOGIC_AGGREGATE_TARGET_NOT_NUMBER`）、`where` の整合、**集計をまたぐ計算の循環**（`LOGIC_COMPUTED_CYCLE`）を見る

### sum

- `sum: <entity>.<項目か計算>`：`where` に合う行の、その項目か計算の値を**足す**（M1.2）
- `count` と同時には書けない（どちらか一方である）
- 対象は**数**でなければならない。文字列・参照（値は ID の文字列）・参照の並びは `LOGIC_AGGREGATE_TARGET_NOT_NUMBER`
- 合う行が 1 件も無ければ **0** である（空の集計は 0。Q3）
- **合う行の対象の値に `null`（有限の数でなくなった計算など）が 1 つでもあれば、合計も `null` にする。** 空集合の 0 と区別し、**黙って 0 に読み替えない**（2026-09-16 窓口が決定）。画面は `null` を「—」で見せる

### count

- `count: <entity>`：`where` に合う**行の数**を返す（M1.2）
- `sum`・`avg` と同時には書けない。`count` は値を読まないので、行の値の `null` には影響されない
- 合う行が 1 件も無ければ **0** である

### avg

- `avg: <entity>.<項目か計算>`：`where` に合う行の、その項目か計算の値の**平均**を返す（M1.4。Issue #177）
- `sum`・`count` と**同時には書けない**（`aggregate` に書けるのは 3 つのどれか 1 つである）
- 対象は**数**でなければならない。文字列・参照（値は ID の文字列）・参照の並びは `LOGIC_AGGREGATE_TARGET_NOT_NUMBER`
- **値の無い行（`null`・空・不正な値）は数えない。** 読めた行だけで平均を求める——1 行の欠損で画面全体が「—」になるのを避けるためである（2026-09-19 窓口が決定）
  - **これは `sum` と別の決めごとである。** `sum` は「対象の値に `null` が 1 つでもあれば合計も `null`」である（上の「sum」。1 行でも読めなければ合計は確定できない）。平均は読めた行だけで求められるので、欠損した行を飛ばす
  - 数えた行が 0 件なら **`null`** である（0 に読み替えない。0 件の平均と、0 の平均は別物である）
- **割り算の表示は、小数第 1 位まで（四捨五入）である。** これは**見せ方**の決めごとであって、**値そのものは丸めない**——一覧の応答は求めた数のままで、**画面が小数第 1 位まで見せる**（整数はそのまま見せる。`2000` を `2000.0` にしない）。「1 回あたりの参加 3.5 人」が読める最小の桁である（2026-09-19 窓口が決定）
- `avg` は**行ごとの集計**（`entity` のある計算）にも、**アプリ全体の集計**（`scope: app`）にも書ける

### within

- **集計の対象を期間で絞る**条件である（M1.4。Issue #178）。`where` の中に `{項目: {within: <期間の名前>}}` と書く

  ```yaml
  - name: activityCount
    scope: app
    aggregate:
      count: activity
      where:
        date:
          within: this_month
    type: number
  ```

- **指せるのは `date` の項目だけ**である。日付でない項目は静的チェックが `LOGIC_AGGREGATE_WHERE_TYPE_MISMATCH` で断る
  - `where` の他の条件（`this` の一致と包含）と同じく、**集計元の entity の項目**を指す
  - `this`（出力先のレコードの ID）を要らないので、**アプリ全体の集計（`scope: app`）でも書ける**（「scope」の節）
- **期間の名前**は閉じている。いま書けるのは **`this_month`（今月）** だけである。知らない名前は
  静的チェックが `LOGIC_AGGREGATE_WHERE_PERIOD_NOT_ALLOWED` で断る
- **「今月」の境目は、日本時間（Asia/Tokyo）の月初 00:00:00 以上、翌月初 00:00:00 未満**である。
  `today()` と同じく**日本時間**で数え、端末の時間帯でも UTC でもない（Q13）
  - 日付の値は `YYYY-MM-DD` である。**同じ桁数の文字列なので、辞書の順が暦の順と一致する**——
    `2026-09-01 <= date < 2026-10-01` で比べられる（「date」の節）
- **時計は評価に引数で渡す**（Q17）。**式の評価の中で現在時刻を直接読まない**——`today()` と同じ扱いである。
  **API に時計を書き換える入口は作らない**
- 対象の行の `date` が形に合わない（読めない）ときは、**その行は合わないものとする**——条件に合わないのと
  同じ扱いで、0 件にも読み替えない（形は静的チェックと data-api の入力の検査が見ている）

### groupby

> 台帳の語彙の名前は `groupBy` である（宣言に書く欄の名前も `groupBy`）。**この節の見出しだけが小文字**なのは、
> 台帳の `semantics` 欄の形（`docs/semantics.md#<小文字と数字とハイフン>`）に合わせるためである。

- **見出しごとに分けて数える（合計する）**集計である（M1.4。Issue #179）。`aggregate` の中に
  `groupBy` を書くと、その集計は**1 つの値ではなく「見出しと値」の組の並び**になる（「groups」の節）

  ```yaml
  - name: activitiesByMonth
    aggregate:
      count: activity
      groupBy:
        month: activity.date
      last: 6
    type: groups
  - name: activitiesByKind
    aggregate:
      count: activity
      groupBy: activity.kind
    type: groups
  ```

- **分けられるのは 2 つだけ**である。ほかを指せば静的チェックが `LOGIC_AGGREGATE_GROUPBY_NOT_GROUPABLE` で断る
  - **`enum` の項目**（`groupBy: <entity>.<項目>`）… **値ごと**に分ける。見出しは **`options` のキー**である
  - **`date` の項目**（`groupBy: {month: <entity>.<項目>}`）… **月でまとめる**。見出しは **`YYYY-MM`** である
- **`groupBy` が指す entity は、集計元（`count`／`sum`／`avg` が指す entity）と同じ**でなければならない。
  同じ entity のレコードを、その項目の値で分ける。
- **集計の対象（`sum`・`avg` の項目）は、`groupBy` と同じ entity の数の項目**である。**計算は指せない**
  （見出しごとの集計は、行ごとの計算を解かない）
- **`groupBy` は `type: groups` の計算だけが持つ。** `type: groups` は `groupBy` を持つ集計を要り、
  `scope` も `entity` も持たない（「groups」の節）。**`scope: app` の計算には書けない**——あちらは 1 つの数である
- **`where` は使える**（`groupBy` の前に対象を絞る）。**`this` は書けない**——見出しごとの集計は出力先の
  レコードを持たない（`scope: app` と同じ理由である）。期間の条件（`within`）は書ける（「within」の節）

#### 並びと件数の上限

- **`enum` の見出しは、`options` に書いた順**である（M1.3 のボードの列と揃える）。**値が 0 の見出しも出す**
  （列を消さない）
- **月の見出しは古い順**である（左から右へ時間が進む。棒グラフの読み方に合わせる）。日本時間の**今月**を終わりと
  して、**直近 `last` か月**を返す。**データの無い月も見出しとして出し、0 と数える**（軸を揃えるためである）
- **`last` は月で分けるときだけ書ける**（省略したときの既定は **6**。窓口の決定 2026-09-19）。
  1 以上の整数である。`enum` で分けるときは書けない（見出しは `options` のキーの全部である）
- **同じ値が並んだときも、並びは決まったとおりである。** 見出しの順（月は日付順、`enum` は `options` の順）は
  値に依らない——**安定であることが要件**である（窓口の決定 2026-09-19。「まだ決めていないこと」から移した）
- **合わない行は数えない。** `where` に合わない行・日付が形に合わない行は、どの見出しにも入らない。
  **集計そのものは `null` にしない**——0 件なら `count` は 0、`avg` は `null` である（窓口の決定 2026-09-19）
- **集計元のレコードを読めなければ（見出しごとの計算の entity が一覧に無ければ）`null`** である。
  **空の並び（合う行が無い）に読み替えない**（「computed」の節と同じ約束である）
- **時計は評価に引数で渡す**（Q17）。「今月」は `within` と同じく `clock.ts` でだけ決める

### groups

- **並びを返す計算の型**である（M1.4。Issue #179）。値は「見出しと値」の組の並びで、`aggregate` に
  `groupBy` を書いた計算だけが持つ（「groupby」の節）
- **`entity` も `scope` も持たない。** 1 つの行の値でも、1 つの数でもなく、**アプリ全体で 1 つの並び**だからである。
  `entity` を書けば `SHAPE_KEY_UNKNOWN`、`scope` を書けば `SHAPE_KEY_UNKNOWN` で断る。
  `type` は `groups` であり、`expression`・`settle` は書けない（集計だけである）
- **一覧の列には出さない**（「computed」の節）。真偽（`boolean`。強調が指す）と同じ扱いである——
  **グラフの部品が指すためだけに使う**。`show`（表・一覧の列）に書けば静的チェックが `UI_FIELD_NOT_FOUND` で断る
- **値は一覧の応答の `groups`（計算の名前 → 「見出しと値」の組の並び）に載る。**
  **アプリ全体の集計（`scope`）の欄には混ぜない**——`scope` は「数か `null`」のままであり、
  混ぜると画面が項目ごとに値の型を見分けることになる（`#177` の追記 2）。`rows`・`settlement`・`scope` と
  同じく、**兄弟の欄**である
  - **宣言が無ければ、`groups` の欄そのものを載せない**（`settlement`・`scope` と同じ約束である）
  - **1 回の取得でまとめて返す**（部品ごとに取りに行かない）。**画面は式も集計も評価しない**——値は data-api が求める
  - 組は **`heading`（見出し。月は `YYYY-MM`、`enum` は `options` のキー）** と、**`value`（数か `null`）** を持つ。
    **見出しは保存される値のほうで、画面に出す名前ではない**——画面が表示名に対応づける（月はそのまま、
    `enum` は宣言の `options`）。これは `ref` を ID で送って画面が名前へ写すのと同じ考え方である
  - 値が求められなければ **`null`** である（0 に読み替えない）。画面は「—」で見せ、0 と区別する

### scope

- **計算の範囲**（M1.4。Issue #177）。`computed` の 1 件に `scope: app` と書くと、**アプリ全体で 1 つの値**になる。書かなければ、従来どおり `entity` の**行ごとの値**である
- **アプリ全体の計算は `entity` を持たない**——どのレコードにも属さないからである。`scope: app` に `entity` を書けば `SHAPE_KEY_UNKNOWN`、`settle`（精算）を書けば `SHAPE_KEY_UNKNOWN` で断る（精算する人の entity が要る）。`type` は `number` だけである（真偽は行ごとの強調（`highlight`）が指すためにだけ使う。M1.3）
- **値はアプリ全体で 1 つである。** レコードの数に関わらず、一覧の応答の `scope`（**計算の名前 → 値**）に 1 つずつ載る。**行ごとの値（`rows`）とは別の欄**である
  - アプリ全体の計算を 1 つも宣言していなければ、応答に `scope` の欄そのものを**載せない**（`settlement` と同じ約束である）
  - 求められなかった値は **`null`** である（0 に読み替えない）。画面は「—」で見せ、0 と区別する（「computed」の節）
  - **1 回の取得でまとめて返す。** 部品ごとに取りに行かない。**画面は式も集計も評価しない**——値は data-api が求める
- **参照できるのは、ほかのアプリ全体の計算だけである。** entity の項目も、行ごとの計算も見えない（名前解決が違う）。`.` を使った参照も書けない
  - `sum`・`avg` の集計元は、**entity の項目か、その entity の行ごとの計算**を指せる（`sum: activity.attendeeCount`）。これは行ごとの集計と同じである
- **アプリ全体の集計の `where` に `this` は書けない。** 出力先のレコードが無いので、比べる相手が居ない——書けば `LOGIC_AGGREGATE_WHERE_TYPE_MISMATCH` で断る。**期間の条件（`within`）は書ける**——比べる相手が期間の名前だからである（「within」の節）

### settle

- 精算（M1.2）。**メンバーの差し引きから、送金の組（誰が誰へいくら）を出す**。計算の 3 つ目の形であり、
  `expression`・`aggregate` と**択一**である（同時に書けない）。**`type` を持たない**——値は数ではなく、
  送金の並び（送金元・送金先・**正の**送金額）だからである
- `entity` は**精算に現れる人**である。組の順を決めるのに使う**登録順**は、その entity のレコードの順である
- 宣言は、割り勘の支出の entity と、その entity の 3 つの項目を**名前で**指す
  - `expense` … 割り勘の支出の entity。**同じインスタンス**（同じ Durable Object）のレコードだけを見る（「ref」の節と同じ）
  - `amount` … その支出の額の項目。**数**でなければならない（`LOGIC_SETTLE_AMOUNT_NOT_NUMBER`）。
    精算は**整数円**だけを扱うので、この項目は入力の検査で**小数を断る**（Q18-6）
  - `payer` … 払った人（精算する `entity` を指す参照 `ref`）
  - `shares` … 割る人（精算する `entity` を指す参照の並び `list of`）
- 差し引き額は、**払った額の合計 − 負担の合計**である。正なら受け取る人、負なら払う人、
  **0 なら送金に現れない**（自己送金も現れない）
- 送金の組は、受け取る側と払う側を**それぞれ金額の大きい順**に組にする（**同額は登録順**）。
  **一組を処理するたびに、残額で並べ直す**（Q18-7）。最少送金回数の探索は行わず、件数は
  人数 n に対し**高々 n − 1** である。n = 0、または全員の差し引きが 0 なら**空の並び**である
- 差し引き額は**合計が 0 でなければならない**。非数値・非有限値・合計の不一致は成功の精算結果にしない
  （黙って丸めたり、差額を誰かに寄せたりしない）
- **端数の決めごと（Q13。語彙ではない）**：1 人あたりの基準額は**1 円未満を切り捨てる**。
  `支出額 − 基準額 × 割る人の数` の余りは、**払った人が割る人に入っていれば払った人**が、
  入っていなければ**割る人のうち登録が最も早い人**が負担する。**割る人を書いた並び順では決めない**。
  各人の負担の合計は、その支出の額と**ちょうど一致する**
- **基準額と、個人ごとの配賦を、宣言で混同しない**（Q18-5）。宣言の `owed` は基準額の集計のままであり、
  余りを誰が負担するかは店頭の内部規約として `settle` が解く。**余りの配賦の語彙は足さない**
- 精算の値は **API が返す**（一覧の応答の `settlement`。M1.2）。画面は計算し直さず、その並びを見せる
  （見せ方は「settlement」の節である。M1.2）
- 宣言の検査は、支出の entity の実在（`LOGIC_ENTITY_NOT_FOUND`）、`amount` が数の項目であること
  （`LOGIC_SETTLE_AMOUNT_NOT_NUMBER`）、`payer`・`shares` が精算する entity を指す参照であること
  （`LOGIC_SETTLE_REFERENCE_TYPE_MISMATCH`）を見る

### min

- `min(a, b)`：数を**ちょうど 2 つ**受け取り、小さいほうを返す

### max

- `max(a, b)`：数を**ちょうど 2 つ**受け取り、大きいほうを返す。0 で割らないための守り（`x / max(1, n)`）にも使う

### len

- `len(xs)`：`list` を**ちょうど 1 つ**受け取り、要素の数を返す。文字列や数は受け取らない

### today

- 店頭が用意した関数（M1.3）。**日本時間（Asia/Tokyo）の「今日」**を、`date` の値（`YYYY-MM-DD`）として返す。
  「今日」は利用者の端末の時間帯ではなく**店頭の時計**で決める（Q13）
- **引数を取らない。** `today(1)` のように渡すと、静的チェックが `LOGIC_FUNCTION_ARITY_MISMATCH` で断る
- 時計は**評価に引数で渡す**（Q17）。**式の評価の中で現在時刻を直接読まない**——採点は時計を固定した
  unit テストで行い、staging の e2e は時計に依存しない値と SHA の照合だけを見る
- 値は日付なので、`computed` の `type: number` には入らない。使うのは比較の式（「date」の節）である

### action

- 操作。`name` と `entity` を持ち、**種類（`kind`）を書ける**（M1.2）。**`kind` を省略すると `create`** である
  （M1.1 の宣言をそのまま読めるようにする。`kind` を書いた `action-with-kind` の宣言は、`create` の正例である）
- `kind` に書ける語は **`create`・`update`・`delete` の 3 つだけ**である（語彙は閉じている）。
  ほかの語は静的チェックが `LOGIC_ACTION_KIND_NOT_ALLOWED` で断る。**何をするかは `kind` が決める**——
  `create` は「create」の節、`update` は「update」の節、`delete` は「delete」の節である
- 入力は「項目名: 値」のオブジェクト。宣言の項目をちょうど全部持つ。計算の名前・`id`・`createdAt` など、
  項目でない名前が入っていたら受け取らない（`create`）。`update`・`delete` は**対象のレコードの ID を取る**
- 検査は `validation` の節の順で data-api が行い、通ったものだけを保存する
- **M1.3 で `set`（決まった値への書き換え）と `when`（その行で操作してよい条件）を足した。**
  **書ける欄は `kind` が決める**（語彙は閉じている）
  - `kind: update` … 上に `set`・`when`
  - `kind: delete` … 上に `when`（書き換える値は無い）
  - `kind` を書かない操作と `create` … どちらも書けない（対象の行が無いので、行ごとの条件も書き換えも無い）
- 書けない欄を書くと、静的チェックが `SHAPE_KEY_UNKNOWN` で断る（一覧の `show` と同じ扱いである）
- 書き込みには `write` の権限が要る（「permission」の節）。権限を強制するのは data-api だけである

### create

- 1 件の追加（M1.2）。**`kind` を省略した操作もこれである**（M1.1 の宣言の意味を変えない）
- 入力は「項目名: 値」のオブジェクト。宣言の項目をちょうど全部持つ
- `id`・`createdAt`・`updatedAt` は店頭が付ける。**入力の値では決まらない**
  （`workspace/mvp/m1/02-l2-spec-examples.md` §1）
- 成功の応答は 201 で、**書いた行**（計算値つきの `ApiRow`）を返す

### update

- 対象のレコード **1 件の置換**（M1.2。`kind: update`）。入力は `id`（対象のレコード）と、
  **宣言した項目の全部**である（`{id: <ID>, <項目>: 値, …}`）
- **`set` を書いた操作だけは別である**（M1.3）——入力は `id` だけで、書き換わるのは `set` に書いた
  項目だけである（ほかの項目は保存された値のまま）。詳しくは「set」の節にある
- **全項目の置換である**（部分更新ではない）。欠けた項目は未入力として型の検査に掛かり、
  `INPUT_REJECTED`（422）になる——**既定値を持つ選択肢（`enum`）の項目だけは、欠けていれば既定値が入る**
  （M1.3。保存の時点で入れるので `create` と同じである。「default」の節）。
  `id` は対象を指すために取り、**保存する値には入らない**
- **`id` と `createdAt` は保持する。変えられない。** 入力に `createdAt`・`updatedAt`・別の `id` を
  混ぜることはできない——宣言の項目に無い名前として `INPUT_REJECTED` になる（`ID や作成日時の書換えを拒否する`）
- 保存する**レコード全体**に、`validation` の節の順（型 → 計算 → 検査の式）と、`ref` の節の
  参照の検査（同じインスタンスの参照先に実在するか）を適用する。**断ったら元のデータと日時をそのまま残す**
- 対象のレコードが無ければ 404 `NOT_FOUND`。`write` が無ければ 403 `PERMISSION_DENIED`
- 成功の応答は 200 で、**書き換えた行**（計算値つきの `ApiRow`）を返す。**`updatedAt` だけが進む**
  （`createdAt` と `id` は変わらない）
- 成功のあと、一覧・集計・精算は**保存された値から読み直される**（計算の値は保存しない。
  「computed」「aggregate」「settle」の節）

### delete

- 対象のレコード **1 件の削除**（M1.2。`kind: delete`）。入力は `id`（対象のレコード）だけである
- **参照されている行は消せない。** 同じインスタンスの宣言にある**すべての** `ref` と参照 list を調べ、
  対象を ID で指す**保存済みの行が 1 件でもあれば**断る（`workspace/mvp/m1/00-open-questions.md` Q13）
- 断ったときの応答は **409 `REFERENCE_IN_USE`** で、**参照元の entity と項目、件数**（`references`）を返す。
  **元の行は変えず、参照元も消さない**——参照を一緒に消す動作にも、削除済みの名前だけを残す動作にもしない
- 対象のレコードが無ければ 404 `NOT_FOUND`。`write` が無ければ 403 `PERMISSION_DENIED`
- **参照の確認と削除は 1 つの Durable Object の中で原子的に行う。** data-api は「どの entity のどの項目が
  対象を指すか」を渡し、DO が同じ書込の中で数えて消す。**独立した RPC を順に `await` するだけにしない**
  ——確認の後に別の操作が参照を足しても、孤立した参照を残さない（`deleteRecordGuarded`）
- 別インスタンスのレコードは、この DO に無いので削除を妨げない。参照元の参照を外す（その行を直す・消す）と消せる
- 一覧の行には、消せるかどうかの材料として**参照している行**（`ApiRow.references`）を載せる
  （その entity に `delete` の操作を宣言しているときだけ）。**画面は参照がある行に削除ボタンを出さず、
  理由を表示する**——`03-spec-layers-and-checker.md` §2.2「画面の非表示だけでは守れない」ので、
  守りは data-api 側（この節）に置く

### set

- **決まった値への書き換え**（M1.3）。`kind: update` の操作にだけ書ける。
  「項目名: 決まった値」を並べた写像である

  ```yaml
  - { name: finish, entity: task, kind: update, set: { status: done }, when: 'status != "done"' }
  ```

- **`set` を書いた操作の入力は `id` だけ**である。ほかの項目を送ると、`update` の全項目の置換ではなく
  **余分な入力として断る**（`INPUT_REJECTED`）。書き換わるのは `set` に書いた項目だけで、
  **ほかの項目は保存された値のまま**である
- **書けるのは決まった値だけで、式は書けない。** 式を許すと計算と操作の境目が消える——
  `estimate + 1` や `today()` は静的チェックが `LOGIC_ACTION_SET_NOT_CONSTANT` で断る
- **値は、その項目の型に合っていなければならない**（`LOGIC_ACTION_SET_TYPE_MISMATCH`）
  - `number` … 数の定数（`3`・`-1`・`1.5`）
  - `date` … `YYYY-MM-DD`（「date」の節）
  - `enum` … `options` の**キーのどれか**（表示名ではない。「enum」の節）
  - `string` … 文字列（式にならない字面だけ）
  - `list`・`ref` … **書けない。** 並びと参照先の ID は宣言に埋め込む値ではない
- 宣言に無い項目名を書くと `LOGIC_ACTION_SET_FIELD_NOT_FOUND` である
- 書き換えたレコード全体に、`validation` の節の順（型 → 計算 → 検査の式）を当てる。
  **断ったら元のデータと日時をそのまま残す**
- 成功の応答は 200 で、**書き換えた行**（計算値つきの `ApiRow`）を返す。`updatedAt` だけが進む

### when

- **その行で操作してよい条件**（M1.3）。`kind: update`・`kind: delete` の操作に書ける。
  **その entity の 1 件について評価する真偽の式**である（`validation` と同じ式の書き方）
- **これはロジック層の守りであって、画面の飾りではない**
  （`workspace/mvp/m1/03-spec-layers-and-checker.md` §2.2）。次の 2 つを**両方**行う
  - **Data API は、`when` が偽の行に対する操作を断る。** 画面が送ってきても断る（唯一の権限強制点）
  - **画面は、`when` が偽の行ではそのボタンを出さない**（親切であって、守りではない）
- 断ったときの応答は **409 `ACTION_NOT_ALLOWED`** で、**どの操作（`action`）のどの条件（`when`）か**を返す。
  **`INPUT_REJECTED` を使い回さない**——「入力が悪い」と「いまその操作はできない」は別物である
- 判定は**保存された行の値**で行う。式が真にならなければ（偽・値が求まらない、のどちらでも）断る
- 一覧の行には、判定の結果として**いま実行してよい操作の名前**（`ApiRow.allowedActions`）を載せる
  （その entity の操作が 1 つでも `when` を持つときだけ）。**画面は式を評価しない**——
  この並びをそのまま見て、ボタンを出し分ける
- 式が真偽にならなければ、静的チェックが `LOGIC_ACTION_WHEN_NOT_BOOLEAN` で断る
- **`enum` の項目を `options` に無いキーと比べたら落ちる**（`LOGIC_ENUM_KEY_NOT_FOUND`）——
  `status == "todu"` の打ち間違いは、動かす前に止まる

## UI 層

### view

- 種類の指定の無い一覧は、**その entity のすべてのレコードを、登録した順（古いものが先）に並べる**
- 各行には、項目を宣言の順に、続けて計算の値を宣言の順に並べる
- **M1.2 で `type`（一覧の種類）を足し、M1.3 でボード（`board`）と一覧（`list`）を足した。**書けるのは
  `table`（表）・`settlement`（精算の表示）・`board`（ボード）・`list`（一覧）だけで、**書ける欄も
  `type` が決める**（語彙は閉じている）
  - `type` を書かない一覧（M1.1 と同じ）… `name`・`entity` だけ
  - `type: table` … 上に `show`（表に出す名前の順。M1.2）
  - `type: settlement` … 上に `type` だけ。`show` は書けない（列の並びを持たない）
  - `type: board` … 上に `columns`（必須）と `highlight`（任意。M1.3。「board」の節）
  - `type: list` … 上に `show`（任意。扱いは `table` と同じ）と `filters`（任意。M1.3。「filters」の節）
- **知らない種類は書けない**（`SHAPE_KEY_UNKNOWN`）。`type` を書かない一覧の意味は M1.1 から変えない
- 一覧は 1 つが 1 つのタブになる（`02` §2.1）。**並べ替え（`sort`）は M1.4 以降の語彙**である
- **`list` は、データ層の項目の型 `list`（文字列の並び）と同じ語である**——1 つの語が 2 つの層に現れるのは
  この語だけである（語彙の台帳は 1 行 1 語彙なので、画面の種類の側は台帳に行を分けず、この節で扱う）

### table

- 表（M1.2）。その entity の項目と計算を**列**に並べる（`03` §2.3「計算はロジック層、見せ方は UI 層」）
- `show` に、**同じ entity の項目と、行ごとの値になる計算の名前**を並べる。**書いた順が列の順**である。
  書かなければ、項目（宣言の順）に続いて計算（宣言の順）である
- 実在しない名前は静的チェックが `UI_FIELD_NOT_FOUND` で断る。**精算（`settle`）の名前は列にできない**
  （値が数の並びではない。API の一覧の応答にも、列として出ない）
- 行の順は API が返した順（登録順）のままである。画面は並べ替えも絞り込みもしない
- **4 つの状態**（`04` §7.3）
  - **空**：行が 1 件も無ければ「まだ記録がありません」を出す。表は描かない（列の見出しも出さない）
  - **多い**：列が増えても**表だけを横に流す**（`.table-scroll` の中に入れる）。
    **幅 360 CSS px で、ページ全体を横に押し広げない**
  - **エラー**：一覧を読めなかった理由（未存在・権限不足・通信失敗）をその場に出す。表は描かない
  - **権限なし**：`read` が無ければ API が 403 を返す。画面は「このアプリを表示する権限がありません」を出す
    （**どの一覧を出せるかは data-api が決める。画面の出し分けは守りではない**。`03` §2.2）

### settlement

- 精算の表示（M1.2）。**API が返した送金の並び（一覧の応答の `settlement`）をそのまま見せる**。
  画面は `settle` を計算し直さない（`03` §2.3「精算の期待値を画面なしで採点できる」）
- 送金元・送金先は **member のレコードの ID** である（`ApiTransfer` の `from`・`to`）。
  画面が **member の名前に対応づけて**見せる（名前は、その entity の先頭の `string` の項目）。
  対応を引けない ID は**消さずにそのまま出す**。「分からないものを消す」より、分かる範囲をそのまま見せるほうが正直である
- 額は**整数円**である（Q18-6）。3 桁の区切りを入れて出す（`C さん → A さん 3,000 円`）
- 宣言は `type: settlement` と `entity`（精算に現れる人）だけである。その entity に `settle` の計算が
  宣言されているとき、API が送金の並びを返す（「settle」の節）。**宣言が無ければ応答に欄が無い**
- **4 つの状態**（`04` §7.3）
  - **空**：送金の並びが空（`[]`。全員の差し引きが 0、または精算する人が 1 人以下）なら
    **「送金は要りません」**を出す。空欄にも「0 円」の行にも読み替えない
  - **多い**：行が多いときは縦に伸びる。**幅 360 CSS px で崩れない**（長い名前は折り返す）
  - **エラー**：`settlement` が `null`（支出のレコードを読めなかった）なら「精算の結果を表示できません」を出す。
    **空の並び（送金が要らない）に読み替えない**（「computed」の節の `null` と同じ約束である）
  - **権限なし**：`read` が無ければ API が 403 を返す。画面は「このアプリを表示する権限がありません」を出す

### board

- ボード（M1.3。`04` §7.2・§7.3）。**`columns` が指す選択肢（`enum`）の項目の値ごとに列を作り、その列にカードを並べる**
  （`02` §3 の見本）。`type: board` と、`columns`（必須）・`highlight`（任意）を書く
- **`columns` は、その entity の選択肢（`enum`）の項目を指す。** 選択肢の項目でなければ、静的チェックが
  `UI_BOARD_COLUMNS_NOT_ENUM` で断る
  - **列の並びは、`columns` が指す `options` に書いた順**である（「enum」の節）。キーを書いた順が列の順になる
  - **空の列も出す。** カードが 1 枚も無い列（値がそのキーの行が 0 件）も、列として見える
    （タスクが 0 件の状態でも、列そのものは消えない）
  - 値が `options` のキーに無い行は、どの列にも入らない（データは data-api が作るので、通常は起きない）
- **`highlight` は、その entity の真偽を返す計算（`type: boolean`）の名前を指す**（任意）。真偽を返す計算でなければ、
  静的チェックが `UI_HIGHLIGHT_NOT_BOOLEAN` で断る
  - 判定は **Data API が行い**、結果を一覧の行の `computed` に載せる（その計算の名前で引ける）。
    **画面は式を評価しない**（`CLAUDE.md` の不変条件）。真の行に印を付ける
  - **`boolean` の計算は列に出さない**（一覧の応答の `computed` の並びには入らない。「computed」の節）
- **強調は色だけに頼らない**（`04` §7.2）。色が分からなくても分かる**記号と文字**を添える（色覚に依らない印）
- **1 列に並べるカードの数には上限を置かない**（上限は M1.5 で決める。`workspace/mvp/m1/measurements.md` §6）。
  ただし**多いときに画面が壊れない**ことは確かめる（下の「多い」）
- **4 つの状態**（`04` §7.3）
  - **空**：行が 1 件も無ければ「まだ記録がありません」を出す。**列は描く**（空の列も出すためである）
  - **多い**：列もカードも縦に伸びる。**列は折り返し（`flex-wrap`）、横には流さない**——
    **幅 360 CSS px で、ページ全体を横に押し広げない**
  - **エラー**：一覧を読めなかった理由（未存在・権限不足・通信失敗）をその場に出す
  - **権限なし**：`read` が無ければ API が 403 を返す。画面は「このアプリを表示する権限がありません」を出す
    （**どの一覧を出せるかは data-api が決める。画面の出し分けは守りではない**。`03` §2.2）

### label

- **画面に出す名前**（M1.3。Issue #176）。項目の名前は `^[A-Za-z][A-Za-z0-9]*$` に限られている
  （式の中で名前として読むため）ので、**識別子とは別に、画面に出す名前を宣言できるようにする**。
  **付けられるのは項目（`fields`）と計算（`computed`）の 2 つだけ**である
  - entity・一覧（`views`）・操作（`actions`）には付けない。書けば静的チェックが `SHAPE_KEY_UNKNOWN` で断る
  - **任意**である。書かなければ識別子（項目名・計算の名前）をそのまま出す
  - **空でない文字列**で書く。空文字は `SHAPE_LABEL_EMPTY`、文字列でなければ（並び・写像）`SHAPE_LABEL_INVALID`
- **1 語の型（`string`・`number`・`list`・`date`）に付けるときは、写像の形で書く**。`label` は欄なので、
  1 語のスカラ（`title: string`）には書けない

  ```yaml
  entities:
    - name: task
      fields:
        title:
          type: string
          label: やること
        due: date            # label を書かなければ、識別子 due のまま画面に出る
  computed:
    - name: overdue
      entity: task
      type: boolean
      label: 期限切れ        # 強調の印の文字になる
      expression: due < today()
  ```

- **画面に出すためだけに使う。式からは読めない。** 式が読むのは識別子だけである（混ぜると名前解決が
  2 通りになる）。`label` を名前として参照する式は `LOGIC_REFERENCE_NOT_FOUND` で断る
- **保存される値は変わらない。** `label` は宣言の中だけの飾りである（レコードにも、正規化した JSON の
  値にも現れない。表示名は**一覧の応答の `labels`** に「名前 → 表示名」として載る）
- **Data API が応答に載せ、画面がそれを読む。** `packages/appspec-schema/src/api.ts` が形を決め、
  `displayNameOf`（無ければ識別子）を SDK と画面が共有する。**同じ読み方をする**（`json の形は 1 か所で決める`）
- **強調（`highlight`）の印の文字は、`highlight` が指す計算の `label`**である（無ければ識別子のまま。「board」の節）
- 追加フォームの入力欄の見出しにも使う。ただし**送る値は識別子のまま**である（宣言の名前が変わらない。
  「entity」の節）

### filters

- **画面が選んで絞り込む**ための UX 層の語彙である（M1.3。`03` §1・`04` §7.1）。`type: list` の一覧にだけ書ける
  （ほかの種類は列の並びを持たない）。宣言では、絞り込みに使う**項目の名前**を並べる

  ```yaml
  - name: taskList
    type: list
    entity: task
    show: [title, status, assignee, due]
    filters: [assignee, status]   # 画面で「担当」「状態」で絞り込める
  ```

- **指せるのは `show` に並べた名前のうち、選択肢（`enum`）か参照（`ref`）の項目だけ**である。
  値の候補を宣言から機械で出せるのが、この 2 つの型だけだからである
  - 指せる**値の候補**：`enum` は `options`（**送るのはキー、見せるのは表示名**）、`ref` は参照先の一覧
    （view）の行（**送るのは ID、見せるのは名前**）。**画面は候補を勝手に作らない**
  - `show` に無い名前は `UI_FILTER_FIELD_NOT_SHOWN`、`enum` でも `ref` でもない項目は
    `UI_FILTER_FIELD_NOT_FILTERABLE` で、静的チェックが断る
- **選択肢には「すべて」を入れる。初期状態は「すべて」**である（絞り込んだ状態では始まらない）
- **絞り込みは画面の中で行う。** Data API には絞り込みの引数を足さない——M1.3 では読むのは今までどおり
  **全件**である（上限は M1.5。`workspace/mvp/m1/measurements.md` §6）。**画面が絞ることは守りではない**
- **選んだ値は、再読み込みで消えてよい。** M1.3 では持ち回さない（URL にも保存にも残さない）——
  保存したい要望が出てから語彙にする（`04` §7.4）
- **4 つの状態**（`04` §7.3）
  - **空**：行が 1 件も無ければ「まだ記録がありません」を出す。**絞り込んだ結果が 0 件のときは、行が
    1 件も無いときとは別の文言**（「条件に合う記録がありません」）を出す——**空欄にも「まだ記録がありません」
    にも読み替えない**。絞り込みの選択肢は出したままにして、選び直せるようにする
  - **多い**：行は縦に伸びる（上限は M1.5）。**表のように横に流さない**——
    **幅 360 CSS px で、ページ全体を横に押し広げない**
  - **エラー**：一覧を読めなかった理由（未存在・権限不足・通信失敗）をその場に出す
  - **権限なし**：`read` が無ければ API が 403 を返す。画面は「このアプリを表示する権限がありません」を出す
    （**どの一覧を出せるかは data-api が決める。画面の出し分けは守りではない**。`03` §2.2）

## 権限

### permission

- `read` は一覧を見ること、`write` は操作を行うこと。`subject` は `minIdentity` だけで、「`minIdentity` を満たす人」を意味する
- 宣言していない権限は、誰にも与えない（`write` が無ければ、操作は断る）
- 権限を強制するのは data-api だけである（Data API が唯一の権限強制点）

### anonymous

- `minIdentity: { mode: anonymous }` は、ログインを求めないことを意味する。**インスタンスの URL を知っている人は、誰でも読み書きできる**（`workspace/mvp/m1/README.md` §7.3）
- ログインが無いので、production では `/api/*` を開けない（Q5）。dev と staging だけで動く

## 宣言の差し替えと、保存済みのデータ（M1.4・#175）

> **この節は、語彙の意味ではなく、置いてある宣言を差し替えるときの決めごとである。** 語彙の台帳（[`../vocabulary.yaml`](../vocabulary.yaml)）には行を持たない。
> 正本は実装である（`packages/control-plane/src/publish.ts` の `isReplaceableDeclaration` と `planReplacement`、`packages/control-plane/src/registry.ts` の `replaceInstance`。unit は `publish.test.ts`・`registry.test.ts`）。

### 2 つの道：暗黙に差し替えない（既定）と、はっきり差し替える（`--replace`）

- publish は、既存インスタンスが**別の原本**（SHA-256 が違う宣言）を指していると、**既定では断る**（`instance_conflict`）。**これは安全のための設計であって、不具合ではない**——同じリンクの中身が黙って入れ替わると、そのリンクを使っている人の記録が別の意味になる
- **はっきり差し替える**ときは、`publish ... --replace` を付ける（`infra/scripts/publish.ts`。`deploy-staging` の ⑤publish はこれを付ける）
- `--replace` でも、**差し替えてよい宣言でなければ断る**（`replacement_conflict`。`app_conflict` とは別の誤りコードである）。断るのは、保存済みのレコードの**読み方を変える**差し替えだけである
  - **entity の名前を変える・消す**（前の宣言の entity が、後の宣言に同じ名前で無い）
  - **項目を消す**（前の宣言の項目が、後の宣言の同じ entity に無い）
  - **型を変える**（`string`・`number`・`list`・`date`・`ref` の参照先・`list of` の参照先・選択肢（`enum`）のキーが変わる）
- **足すのはよい。** entity・項目・選択肢のキーを足す差し替えは通る。**表示名**と **`default`** は、**保存される値**（キーと、既に保存された値）を変えないので、変わってよい
- **データ層（entity と項目）以外は見ない。** `views`・`actions`・`validations`・`computed`・`permissions`・`minIdentity` は差し替えてよい（見せ方とロジックの変更は、保存済みの値の読み方を変えない）
- **断ると分かった時点で止める。** 差し替えの下調べは **R2 の読み取りだけ**を行い、**R2 にも D1 にも書かない**——登録簿の行も、新しい原本のオブジェクトも残らない（断られる差し替えを置きに行かない）
- 差し替えても、**登録簿の行は壊れない**。変わるのは `app_instances` の指す先（`source_sha256`）だけである。前のアプリの行（`apps`）と、前の原本の R2 のオブジェクトは**消さない**（巻き戻すときの材料である）

### 保存済みのレコードはどう読まれるか

- **レコードは、そのまま残る。** 差し替えは宣言の指し先を変えるだけで、**1 インスタンス 1 つの Durable Object のレコードには触れない**（作り直さない・消さない・書き換えない）
- **後の宣言で足した項目**は、前の宣言で作ったレコードには**無い**。そのレコードでは、その項目を**未入力として読む**
  - **選択肢（`enum`）の項目に `default` があれば、その既定値が入っているものとして読む**（「default」の節）。**無ければ未入力のまま**である
  - 未入力の値は、**0 にも空文字にも読み替えない**（「computed」の節の `null` と同じ約束である）
  - 既定値が入るのは**保存の時点**なので、**その後で書いたレコード**には入る。前のレコードを後から埋め直すことはしない
- **前の宣言にあった項目を消す差し替えを断る**のは、この読み方から出ている。消えた項目の値を「未入力」と読むと、その値は**どこからも見えなくなる**（黙って捨てたのと同じになる）。消したいときは、**新しいインスタンス ID を作る**（データを作り直す）か、**使わないまま残す**かを選ぶ——どちらにするかは人が決める
- **記録の移行（変換）はしない。** これを書いている時点で、**保存された値に触れる差し替えの道は無い**（足すだけの差し替えだけを通している）。「同じリンクのままアプリが直る」（M2.4）の先取りである

### 同時に publish したとき（競合）

- 同じインスタンスへ**同時に 2 つの deploy が publish** しても、**登録簿の行は壊れない**。差し替えは `app_instances` を **「前の SHA-256 が一致する行だけ書き換える」**（compare-and-swap。`replaceInstance`）ので、**負けた側は行を変えない**
  - 負けた側は `instance_conflict` で止まる（**黙って上書きしない**）。**次の deploy が同じ原本を置けば収束する**
  - **同じ原本**（同じ SHA-256）を置いた 2 つは、どちらも成功する（2 つ目は「既に差し替わっている」を読むだけである）。だから `deploy-staging` は、**同じ見本を 2 回続けて置いても落ちない**
  - `deploy-staging` は `concurrency: { group: deploy-staging, cancel-in-progress: false }` で直列化する（`.github/workflows/deploy-staging.yml`）。この compare-and-swap は、その外側から手で publish したときのための安全網である
- **e2e のデータとデモのデータを混ぜない。** e2e は後片付けでレコードを消すので、**デモ用のインスタンスを e2e と同じ ID にしない**（2026-09-19 の M1.3 で実際に踏んだ。`workspace/mvp/m1/demos.md`）
  - e2e の見本は、**e2e 専用の固定 ID**（`m12-e2e-warikan`・`m12-e2e-task-board`）へ置く
  - デモは**デモ専用の ID**（`m11-demo-expense-log`・`m12-demo-warikan`）へ置く。**同じ ID を使い回さない**

### 失敗したあとの後片付け

- **失敗しても、同じ入力を再実行すれば正しい状態へ到達する**（R2 は同じキーへの上書き、D1 の登録は冪等）。`PublishFailure.stage` が、どこで止まったかを示す
- **`replacement_conflict` は決定である。** やり直しても同じ結果になる。直すのは次のどちらかで、**どちらにするかは人が決める**
  - 差し替えてよい宣言に直す（消した項目を戻す・型を戻す・entity の名前を戻す）
  - **新しいインスタンス ID を作って、そこへ置く**（前のデータを見る必要があるなら、前の ID を残す）
- 差し替えの途中で落ちたとき（R2 は置けたが登録簿に届かない）も、**登録簿の行は前のままである**（途中まで書いて止まらない）。次の deploy が同じ原本を置けば、`--replace` が最後まで進む
- **登録簿の行と、R2 の古いオブジェクトは消さない。** 巻き戻すときは、前の SHA-256 を指すように戻す（**前の宣言と、そのデータはそのまま残っている**）
