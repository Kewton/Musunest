# 窓口の運用：委任・見張り・レビュー

窓口（main の Claude）が、管理・レビュー役・調べ役へ頼み、その結末を取りこぼさないための決まりと罠である。
並列開発の手順の正本は [`docs/parallel-development.md`](../parallel-development.md)。ここはその補い。
2026-11-18 に、窓口の Claude Code の auto memory から移した（#968）。

## 1. 誰に頼むか

| 役 | 宛先（alias から解決する。instance-id を推測しない） | 頼むこと |
|---|---|---|
| 管理 | main の Command Code（`command-code`） | `cmate-orchestrate` での並列開発（CLAUDE.md の「開発の進め方」） |
| 管理の代わり | Claude_dev_sub（`claude-3`） | Command Code が利用の上限・認証の失効で使えないとき。ワーカーのモデルは Issue の難しさで分ける（工場の判定・門・複数パッケージは Opus、試験・注記だけの小さい Issue は Sonnet）。依頼文に書く |
| レビュー | Claude_sub（`claude-2`） | 起票前の Issue の下書き・設計・wave の候補の独立レビュー（2026-11-11 所有者が指定。それまでは Codex） |
| 調べ・採点 | Codex（`codex`）・Claude_dev_sub | 原因の調べ・正解の表での採点（側を伏せる） |

- Command Code に戻すのは、所有者が言ってから（2026-10-29 の実例）
- 止まっているレビュー役・調べ役は起動してよい（開発体制のセッションの起動は許可済み）
- 既に Codex に送る段取りが組んであるものは、所有者に断らずに付け替えない

## 2. 送る前

- **送るたびに `/clear` か `/compact` を選ぶ。省かない**（所有者 2026-10-10・10-11・10-14）
  - 新しい wave・別の Issue・自己完結の依頼文 → `/clear`
  - 同じ wave の続き（停止への返事・直し・merge の指示・統合候補の作り直し）→ `/compact`
  - 送ったら `wait --on-prompt agent` で入力待ちに戻ったのを確かめてから本文を送る。迷ったら前提を書き足して `/clear` に倒す
  - 理由：依頼のたびに文脈が積み上がり、プランの枠と文脈を無駄に使う（wave 25 で compact により約 11.8 万トークン減った）
- 管理へ送る前に、Command Code の画面で利用の上限の表示を確かめる。超えていたら Claude_dev_sub へ送る
- **実行契約は Issue の `## 守ること` を転記しない**（#384 で実測）。禁止事項（封を読まない・外部 API を呼ばない など）は、管理が「ワーカーのターンが終わって入力欄が空いたら最初に送る追加メッセージ」で届けるよう依頼文に書く
- Issue の地の文で、**「依存」「のあと」「前提」などの方向語と別の Issue の `#番号` を同じ行に書かない**。planner は `--no-infer` でも、否定を含めて依存の edge と読む（#363 で閉路）
- 調べの依頼文の形：原因ごとに 観察（記録の引用）→ 根本の原因（ファイル:行）→ 案の比較と推奨 1 つ → 書き換えるファイル（試験も具体名）→ 費用。共通の直し方と「確かめていないこと・推測」を分ける。結果は `workspace/mem/requests/<name>.result.md` 1 本、締めは `DONE:` の 1 行

## 3. 見張る

止まる経路（判断待ち・読み替えの申告・入力欄の候補）は git にも GitHub にも跡を残さない。

- **状態ファイルで待つ**：長い依頼では、止まるとき・段が終わるときに `workspace/mem/requests/<name>-status.md` の行を書き換えさせ、窓口はそのファイルの変化を条件に入れて待つ。PR の数や branch の head だけを見ない（2026-10-16 に 77 分、10-18 に約 2 時間気づけなかった）。見張りには上限時間も付ける
- **止まったら窓口へも送らせる**：状態ファイルに書いた直後に `commandmate send musubi "<一言>" --instance claude`（10-17 に約 2 時間気づけなかった）
- **DONE 行は画面とファイルの両方で見る**：Codex は DONE を画面にだけ出すことがある（10-14 に約 2 時間）。依頼文の締めに「DONE の行は結果のファイルの最終行にも書く」と書く
- **DONE 行の見張りは言い回しに依らない**：止まり方の文言を正規表現で当てず、新しい `DONE:` 行なら何でも起きる形にする。古い DONE 行と依頼文の雛形（`<` を含む行）だけを除く（10-19 に 4 時間）
- **入力欄の候補は送られていない**：ワーカーの入力欄に「push して PR を作って」と見えても送信されていないことがある。DONE の時刻と push・PR の有無を照らし、DONE から 15 分を超えて PR が無ければ知らせる（10-17 に 3 ワーカーが 2.5 時間）
- **Command Code の plan の承認画面**：`REVIEW`・`Approve ctrl+a` の画面には auto-yes が答えない。送ってから 10 分ほどで画面を確かめ、出ていれば所有者の承認を得て `commandmate respond musubi --instance command-code --plan-review approve`（直しがあれば先に `--plan-review submit "<comment>"`）。2026-10-30 に 18 時間止まった
- **忙しい管理へ送り直し続けない**：`send` が prompt not ready で入らないとき、背景の loop で送り直すと、済んだ後に古い一言が届く。裁定はまず `requests/w<wave>-<issue>-decision.md` に書く（管理は自分で読む）。送り直しは数分で止める

## 4. シェルの罠（macOS）

- **bash 3.2 で変数の直後に全角文字**：`"…（$VAR）"` は `VAR\xef\xbc` と読まれ `set -u` で落ちる。必ず `${VAR}` と書く。`grep -nP '\$[A-Za-z_][A-Za-z0-9_]*[^\x00-\x7F]'` で検査する
- **`trap … EXIT` と `set -u`**：展開エラーで落ちると終了コードが 0 になることがある。重要な段の成否は、最後の行の完了マーカー（例 `DONE <env>`）でも確かめる（#75 の切り替えで production の段へ進みかけた）
- **`pgrep -f` と日本語のパス**：パターンにマルチバイト文字があると regex の評価に失敗して非 0 を返し、「見つからない」と区別できない。background の操作は PID を控えて `kill -0 <pid>` で見る。使うなら `LC_ALL=C` と ASCII だけのパターン。終了は操作が書く終了行で判定する

## 5. Cloudflare のアカウント

- production のアカウント（②）は手持ちの API トークンで読めない（403）。使用量・請求・CPU をコマンドで取ろうとしない（所有者がダッシュボードで見る）。①の実測を②の根拠に使ってよい
